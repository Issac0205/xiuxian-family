## 一、资源注册表 `src/data/resources.js`

### 1.1 它是什么、不是什么

- **是**：一份**索引式台账** —— 「玩家可见的量有哪些 / 它属哪一类 / 它真正存在哪 / 什么时候才该让玩家看见它 / 开发者模式下补不补」。
- **不是**：第二份真相源。**数值仍然只存在 `state.*` 里**，`path(s, d)` 只是**唯一读法入口**。
  - 禁止的写法：注册表里写 `value: 100` 然后再往 `state.silver` 同步。
  - 允许且要求的写法：`path: (s) => s.silver`，UI / 测试 / 开发者模式全走这一个入口读。
- **不是**：存档结构的一部分。注册表**不进存档、不进 `serialize()`、不进 `hydrate()`**（见 §2.4）。

### 1.2 字段规格（照 `docs/100 §附录 B` 落地，+ 3 个补充字段）

```js
// src/data/resources.js —— 资源台账（唯一索引；数值仍在 state 里）
const RESOURCES = [
  {
    id: 'silver',                  // 稳定 id：存档/断言/测试用，永不重命名、永不删除
    name: '银两',                   // 玩家看到的显示名（同名不同物必须不同名，见 §三.5）
    kind: 'currency',              // currency | material | population | progress | modifier | flag
    group: 'resource',             // resource（货币+材料）| world（人口/进度/属性）| gate（解锁标记）
    path: (s, d) => s.silver,      // ★ 唯一读法入口：返回 number 或 {n:number}；禁止 UI 自己算
    rate: (s, d) => d.silverPerSec,// 可选：每秒产率（非产出型写 null，理由进 note）
    cap:  (s, d) => d.silverCap,   // 可选：上限（无上限写 null）
    gate: null,                    // null = 不门控；否则见 §三.2 的判据对象
    lockedUi: 'hide',              // hide | dim | mask（§四 三口径；必须显式声明，不许默认）
    hint: '开局即有——田地与人口自己会生钱',  // 未解锁时怎么拿；非空中文，与 GUIDE_STEPS 同源
    dev: { give: true, to: (s, d) => d.silverCap },  // 开发者模式语义，见 §五.2
    note: '唯一真相源 = state.silver；上限 = d.silverCap',  // 出处 / 历史 / 为什么不补
  },
  // …（全量清单见 §六）
];
```

**补充字段（相对附录 B）与理由**：

| 字段 | 为什么加 |
|---|---|
| `note` | 主策裁决 ①③ 要求「同名不同物的历史」「散落魔数的出处」**写在注册表里**，否则下次还会有人再混一次 |
| `hint`（附录 B 有，这里设为**必填**） | 附录 C 断言 5：`hide` 口径下玩家看不到数值，**如果还没有 hint 就等于彻底失联** |
| `dev.to` | 附录 B 只说 `dev:'unlimited'|'none'`；但「补到多少」必须**可机械求值**（有上限补到上限、无上限补到 `DEV_ABUNDANCE`），否则实现者只能自己拍一个数 |

**`path()` 的返回值约定（重要，t4 的断言靠它）**：

- 数值型资源（银两/灵石/线索/聚灵符…）→ 返回 **number**。
- 有「数量 + 附加属性」的堆叠型资源（符文存货 `{n, expiresAt}`、法器耐久、丹药保质期）→ 返回 **`{ n: number, meta: any }`**；`n` 是唯一的「数量」读法。
- **永不返回 `undefined` / `null`**：容器项缺失时返回 `0`（写法：`Number(s.cultivation?.alchemy?.herbs?.[id]) || 0`）。
  - 这条是为了让附录 C 断言 1（「新开局与满进度两种状态都能返回数字而不抛错」）**可机械验证**，
    也顺手堵掉本项目的老毛病：`undefined` 一路飘到界面上变成 `NaN` 或 `undefined` 文案。

## 二、解锁状态：**派生，不新增 `state.unlocks`**

### 2.1 决策与理由

**结论：不新增顶层字段 `state.unlocks`。解锁状态一律由 §三 的 `gate` 判据 `unlockOf(state, res)` **当场求值**。**

理由（按重要性排序）：

1. **一个数只能有一个真相源。** 门控的真相源**已经存在**：科技线（`state.techs` / `state.immortalTechs`）、占城（`world.held`）、秘闻（`state.secrets`）、境界（`person.realmIndex`）。再存一份 `state.unlocks` 就是第二份真相源，且是**必须永远与前者同步**的那种 —— 迟早会出现「科技研习了但 unlocks 没写」的静默不一致。
2. **新增顶层字段的代价是 3 处**：`createState()` / `serialize()` 顶层白名单 / `hydrate()`（含默认值）。本项目**已经因此踩过两次**：
   - `immortalTechs` / `morality` / `exchangeCount` 漏在 `serialize()` ⇒ **刷新一次整条仙道科技线归零、道心回 50、兑换次数归 0**，而且当时测试全绿（只查了 `cultivation.*` 内部）；
   - `meta` 更彻底：`hydrate()` 会重建它、`serialize()` 从不写出 ⇒ **每次读档都清空轮回进度**。
   现在 `scripts/smoke.mjs:2431` 有一条结构性断言守着（`createState` 的每个顶层字段都必须在 `serialize()` 里）。
   **不新增字段 = 不可能再犯这一类错。**
3. **派生天然不会「读到过期值」。** 存状态就要考虑：轮回重置时保留吗（`REINCARNATION_KEEP`）、`hydrate` 旧存档补什么默认值、被夹断后怎么修。派生这三件事**全部不存在**。

### 2.2 派生的代价（必须正面承认），以及「可见不回退」怎么处理

派生的唯一缺点：`gate` 求值只依赖**当前状态**，而项目有一条既有约定（`systems/progression.js:19`）：

> **一旦可见就不要再让它消失（除非重开）—— 栏目忽隐忽现比一直显示更让人困惑。**

处理办法：**「可见性」而不是「解锁事实」做粘性，且粘性只做在 UI 层，不进存档。**

- 判据分两层：
  - `unlockOf(state, res)` → **纯函数**：这一刻的客观解锁事实（注册表用，测试用，开发者模式用）。
  - `visibleOf(state, res)` → **界面用**：`unlockOf(...) || stickyVisible(res, state)`。
- `stickyVisible` 的可选实现：读一件**已经存在**的「痕迹量」，不新增字段。例：
  - 资源 `secret`（累计秘闻）一旦 `> 0` 就永不回退 —— 它本身就是只增不减的。
  - `clue`（线索）会花掉，所以粘性读 `secrets.length > 0 || immortalTechs.length > 0`（=「他进过仙途」）。
  - 这类「痕迹判据」**集中登记在 `resources.js` 的 `note` 里**，UI 不许自己现写。
- **⚠ 不能粘的东西**：`lockedUi==='hide'` 的**数值格**。藏起来的东西没有「玩家已经看见过」的痕迹，
  硬做粘性会得到「量是 0、格子还在、还写着 0/上限」的鬼状态。所以资源条走**纯 `unlockOf`**，
  粘性只用在本项目既有的**页签/分块**上（那些已经由 `pageVisible`/`immortalBlockVisible` 处理，本次不动）。

### 2.3 那 `pageVisible` / `immortalBlockVisible` / `techVisible` / `dashboardVisible` 要不要改成读注册表？

**分两步，t3 不改行为、只收敛读法（渐进式）：**

- **第一步（t3 做）**：注册表的 `gate` **复用**这几个既有函数的判据，不复制它们的逻辑。
  - 例如资源 `herb`（药材）的 `gate = { kind:'canAct', of:'alchemy' }` ⇒ 求值直接读 `immortalBlockVisible(state,'alchemy')`。
  - 于是「界面可见集合」与「注册表解锁集合」**在定义上就是同一个函数**，不可能分叉。
- **第二步（可选，后续）**：把四个函数的 `switch` 换成读 `RESOURCE_MAP`，让它们变成注册表的**消费者**。
  这一步**有回归风险**（smoke 里有一整节「界面可见集合 === 已研习 ∪ 前置满足」，`scripts/smoke.mjs:229`），
  所以**不在 t3 的范围**，登记为 t3 之后的收敛项。

### 2.4 反污染硬约束（t4 必须验的一条）

**注册表字段名不得与 `state` 的任何字段同名，否则「派生」会在实现里被误做成「存起来」。**

- 由于 §1.2 的字段名（`id/name/kind/group/path/rate/cap/gate/lockedUi/hint/dev/note`）与 `createState()` 的字段（`silver/population/buildings/techs/…`）**无交集**，这条目前自动成立。
- **验法**：断言 `Object.keys(RESOURCE_MAP.silver).filter(k => typeof k === 'string')` 与 `Object.keys(createState())` 的**交集为空**；
  并且断言 `RESOURCES` 里**不存在**名为 `value` / `amount` / `count` 的字段（那是最容易退化回「存一份」的三个名字）。
- 另一条：**`serialize()` 的键集合不得因为本次改动发生任何变化**（`scripts/smoke.mjs:2434` 已有「serialize 键全都在 createState 里」的断言，本次沿用即可）。

## 三、解锁判据

### 3.1 gate 判据对象（kind → 求值）

| `gate.kind` | 形状 | 求值（**复用既有函数，不另造**） | 用在哪些资源 |
|---|---|---|---|
| `null` | `null` | 恒 `true`（开局即见） | 银两、灵石、人口、容量、岁入、出生/死亡率、田地 |
| `tech` | `{kind:'tech', value:'realestate'}` | `isResearched(s, value)` | 地产、房产、钱庄、演武台… 凡是被科技解锁的**建筑产量类** |
| `itech` | `{kind:'itech', value:'lingtian'}` | `isImmortalTechResearched(s, value)` | 仙道侧的容量/倍率类 |
| `secrets` | `{kind:'secrets', value:10}` | **`s.secrets.length >= value`（累计！）** | 坊市、祛障丹、仙途整页 |
| `realm` | `{kind:'realm', value:22}` | `highestRealmIndex(s) >= value` | 轮回页、化神仪表 |
| `held` | `{kind:'held', value:1}` | `worldOf(s).held.length >= value` | 三类材料（药材/矿料/符文料）、赋税 |
| `canAct` | `{kind:'canAct', of:'alchemy'}` | **直接读 `immortalBlockVisible(s,'alchemy')`** | 丹房/器坊/符房/人丹分块内的一切 |
| `flag` | `{kind:'flag', value:'poolBlueprint'}` | 读那个标记本身（见 3.4） | 只会被标记解锁的**副作用产物** |

**三条硬约束（写进实现与测试）：**

1. **门控判据只有一个来源**：`gate` 由注册表求值，UI **不许**自己写 `if (state.techs.includes(...))`。
2. **`lockedUi` 必须显式声明**，不允许「默认藏」—— 默认值会让人漏项。
3. **`canAct` 是本项目铁律的落点**：凡是「这条生产线出现」类的门控，问「**他现在有事可做吗**」，
   不问「他有没有量」。**`held > 0` 就是那个已经被判过死刑的问法**（它以「有没有量」代理「有没有事可做」，
   在 `docs/100 §七` 已被点名；`immortalBlockVisible` 目前用的是 `held>0 || crafts>0`，
   后半段 `crafts>0` 正是「他做过这件事」的补救，保留）。

### 3.3 `devGive` 的语义（⚠ 这是 t3 的硬约束，主策裁决 e）

```js
dev: { give: false }                              // flag：不是量，无从补
dev: { give: true, to: (s, d) => d.silverCap }    // currency：补到游戏自己承认的上限
dev: { give: true, to: null }                     // 无上限的 currency/material：补到 DEV_ABUNDANCE
dev: { give: false, note: 'population：∞ 会炸 deathRate 的拥挤项' }   // 见下
```

> **`devGive` 只对 `kind ∈ {currency, material}` 生效；**
> **`population` / `progress` / `modifier` / `flag` 一律 `null`（等价于 `{give:false}`）。**
>
> 理由（两条都是死局，不是保守）：
> 1. `population = ∞` ⇒ `derive()` 的拥挤项 `over = max(0, ratio − threshold)/(1 − threshold)`，
>    而 `ratio = pop / housingCap = ∞` ⇒ 死亡率里出现 **`∞²`** ⇒ `state.population = max(0, pop + births − deaths)` 变 `NaN` ⇒ **整个存档烂掉**。
> 2. `realmIndex = ∞` ⇒ `realmInfo(∞)` / `realmDashboardKey` / `xpNeeded(∞)` 全部**越界**（`data/realms.js` 表只有 26 档）。
>
> **并且加一条断言**（t4 照此验，见 §九 A7）：
> 「**`devRefill` 不得改动任何非资源类字段**」——
> 注入 `devMode=true` 跑若干 tick，断言**人口 / 境界 / 各类倍率与未开启时逐字段相等**。

### 3.4 标记类（`kind:'flag'`）不得自我门控

`flag` 记录的是「这件事做过了」。**如果它自己被自己的门控挡住，就是死锁** ——
这正是仙途自锁的形状（当时「仙途可见」被写在仙途内部的数据上）。

**规则：`kind:'flag'` 的 `gate` 只能是「获取它的那个动作的前置」，绝不能是它自己。**
例：`poolBlueprint` 的 `gate` 是坊市门槛（`canAct:'markets'`），不是 `poolBlueprint`。
**校验**：断言里加一条 —— 任何一个 `gate.kind==='flag' && gate.value===该资源 id` 都算**违规**（§九 A8）。

## 四、未解锁的三种口径（主策裁决 ③，照此写死）

`docs/100 §五` 定了三口径，主策已批准，这里**写死为可实现的判据**：

| 口径 | `lockedUi` | 落到 DOM 上的做法 | 用在 | 现状先例（出处） |
|---|---|---|---|---|
| **藏** | `hide` | **该元素根本不渲染 / `hidden`**；不占格子、不进 DOM | **资源条**（各页 `PAGE_RES`）、页签、境界仪表、仙途分块 | `pageVisible`（`systems/progression.js:21`）、`dashboardVisible`（`:163`）、`immortalBlockVisible`（`:100`）、`PAGE_RES`（`ui/app.js:72`） |
| **灰** | `dim` | 元素在，**`is-locked` + 禁用 + `reason` 文案** | **生产面板**（建筑卡 / 丹房 / 器坊 / 符房 / 坊市商品 / 服丹按钮） | `ui/app.js:793` `须研习「${techLabelOf(def.tech)}」`、`app.js:851/916` 的 `is-locked`、`app.js:1141` `需 ${d.secretGoal} 秘闻` |
| **？** | `mask` | 元素在，**标题 `？？？` + `hint`**，数值引文不渲染 | **图鉴（百科）** | `src/main.js:1104` `<h3>？？？</h3>` + `systems/codex.js:39-47` 的 `seen`，开关 `ui.codexShowLocked` |

**组合规则（避免实现时打架）**：

1. 一个资源**只有一种主口径**（注册表里的 `lockedUi`），跨面板出现时**可以变**：注册表给**默认口径**，
   面板可以覆盖（例：`quzhangPill` 在仙途生产面板外是「藏」，在服丹按钮处是「灰」）。
   **覆盖必须显式写在调用处**（`lockedUiOf(res, 'panel')` 这种带面名的读法），不许隐式。
2. **`hide` 口径的资源，其 id 不得出现在任何 `PAGE_RES` 里**（附录 C 断言 4 的原话）。
   实现方式：`PAGE_RES` 的每一项带上资源 id，渲染时先过 `visibleOf`。
3. `mask` 口径**只用于图鉴**（百科的职责是「以后再来看」，藏起来等于没有图鉴）。

## 五、开发者模式规格

### 5.1 开关存在哪

| 东西 | 存放 | 理由 |
|---|---|---|
| **是否开启** | `state.settings.devMode`（boolean） | `settings` **已经在 `serialize()` 白名单里**（`core/save.js:32`）且 `hydrate` 会读它 ⇒ **零新增顶层字段、零漏字段风险** |
| **是否已通过口令校验（本次会话）** | `sessionStorage['xiuxian-family/dev/token/v1']` | ① **不入存档** ⇒ 分享/上传存档不会带开关；② 关掉标签页即失效 ⇒ 下次打开要重新输密码；③ **不需要改 `serialize`/`hydrate`** |
| **口令本身** | `DEV_PASSWORD_HASH`（常量，SHA-256 hex） | **不要把 `3303` 明文写进代码**（单文件产物 `game.html` 任何人可读） |

**默认值（两处都要）**：

```js
// ✅ core/state.js 的 createState()：
settings: { quizMode: 'always', difficulty: 'normal', speed: 1, devMode: false },
//   加这一个键**不需要**改 serialize（settings 整对象写）、**不需要**改顶层白名单断言。

// ✅ core/save.js 的 hydrate()（settings 还原段里，与其他三项并列）：
if (raw.settings && typeof raw.settings === 'object') {
  if (QUIZ_MODE_MAP[raw.settings.quizMode]) fresh.settings.quizMode = raw.settings.quizMode;
  if (DIFFICULTIES[raw.settings.difficulty]) fresh.settings.difficulty = raw.settings.difficulty;
  const speed = Number(raw.settings.speed); if (SPEED_OPTIONS.includes(speed)) fresh.settings.speed = speed;
  // 【docs/101 §5.1】⚠ 只接受严格 true：旧存档（无此字段）→ undefined → false。
  fresh.settings.devMode = raw.settings.devMode === true;
}
```

> **旧存档读进来必然是 `false`**：老存档 `raw.settings.devMode` 是 `undefined`，
> 而这里用的是**严格等值**（`=== true`）而不是 `Boolean(...)`，所以 `"false"` / `1` / `"yes"` 一律 false。
>
> **手改存档也打不开**：`devMode:true` 只是「开关」，**还必须有本次会话的 token**
> （`devModeOn()` 要求两者同时为真）。所以即使有人在存档里写 `true`，**不输密码仍然不生效**。

### 5.2 补满式生效（`devRefill`）—— 不改任何扣减点

**为什么是补满而不是改扣减点**：扣减点散在 `core/engine.js`（研习/购置/兑丹/坊市）、`systems/alchemy.js`、`systems/forge.js`、`systems/runes.js`、`systems/immortal-actions.js`（灵池/矿工/寻龙尺/升炉/升台）、`systems/markets.js`、`systems/breakthrough.js`（突破吃灵石+线索）…
**逐个改必漏**，而漏掉的那一个就是「开发者模式下这条线还是卡住」的 bug。补满式**一次覆盖全部消耗点**，
而且**天然只作用于有量的资源**。

```js
/* src/systems/dev.js（新文件；插在 core/engine.js 之前，manifest 里紧随 systems/progression.js 之后） */

/** 本次会话是否通过口令（sessionStorage 里的 token 等于口令哈希）。 */
function devUnlocked() { /* 读 sessionStorage；读不到 → false */ }

/** 总开关：口令 + settings.devMode 同时为真。 */
function devModeOn(state) {
  if (state?.settings?.devMode !== true) return false;
  return devUnlocked();
}

/**
 * 把「已解锁 且 dev.give 非空」的资源补满到 dev.to()。
 * ⚠ 铁律：**只写 path() 指向的那个字段**，绝不碰 population / realmIndex / 各种倍率 / 上限。
 * ⚠ 上限本身（d.silverCap 等）**不改** —— 改上限会连带改死亡率的拥挤模型（housingCap 参与 crowding）。
 */
function devRefill(state, d = derive(state)) {
  if (!devModeOn(state)) return 0;
  let n = 0;
  for (const r of RESOURCES) {
    if (!r.dev || r.dev.give !== true) continue;      // ⚠ population/progress/modifier/flag 在这里被排除
    if (r.kind !== 'currency' && r.kind !== 'material') continue;  // 双保险（规格 §3.3）
    if (!unlockOf(state, r)) continue;               // 只补「已解锁」的（否则未解锁的坑位会先冒出数字）
    const target = r.dev.to ? r.dev.to(state, d) : DEV_ABUNDANCE;
    if (!Number.isFinite(target)) continue;
    if (writeResource(state, r, target)) n += 1;     // 见下：唯一的写入口
  }
  return n;
}

/** 唯一写入口：数值型直接赋；堆叠型只补 n（不动 expiresAt / 耐久语义）。 */
function writeResource(state, r, value) {
  const cur = r.path(state, derive(state));
  const isStack = cur && typeof cur === 'object' && 'n' in cur;
  if (!isStack) {
    if (!(typeof cur === 'number') || cur >= value) return false;
    setByPath(state, r.holderPath, value);           // holderPath = 注册表里给 devRefill 用的静态写路径
    return true;
  }
  if (cur.n >= value) return false;
  setByPath(state, r.holderPath, value);             // 只改 n；容器自身不动
  return true;
}
```

- **`holderPath`（写路径）与 `path()`（读函数）并列存在**，理由：读要处理「容器缺失 → 0」，
  写要处理「容器缺失 → **不要凭空造容器**」。所以 `devRefill` 对**尚不存在的容器项返回 false（不写）**。
  ⚠ **这里有一条必须写进验收的界**：「已解锁资源补满」指的是**那些容器里已经存在（或开局就存在）的项**；
  数据库里没出现过的项**不补** —— 否则开发者模式会「凭空造出 33 条材料」，把 `crafts>0` 之类的门控全部提前点亮。
  （若产品上确实想要「全材料拉满」，那是**另一条显式开关**，不在本规格内。）
- **`DEV_ABUNDANCE`（无上限资源的补满值）**：`1e12`。
  取这个数的理由：全局最大的单个数字代价是 `MARKET_EXCHANGE_BASE_SILVER = 100000`（`core/config.js:326`），
  后期最贵的升级是「太乙神炉」`silver: 20000000`（`data/alchemy.js:113`）；
  `1e12` 高出 4 个数量级，且**远低于 `Number.MAX_SAFE_INTEGER`（9e15）** ⇒ 不会出现浮点精度丢失。
  银两这一项因为有上限，`dev.to` 是 `d.silverCap`（**不是** `DEV_ABUNDANCE`）——
  补过上限没有意义，还会让 `silver == cap` 与 `silverWasted` 的口径打架。
- **已持有的标记**（`compass` / `poolBlueprint`）：`dev:{give:false}`。
  它们的状态本来就是「已获得」，没有「补满」这回事；去写 `true` 反而会**跳过获取过程**（=跳过坊市花秘闻），
  那是「解锁资源无限」之外的越权。

### 5.3 时序：进入 / 生效 / 关闭

```
【进入】
① 玩家点设置里的「开发者模式」行 → 展开口令输入框
② 输入 3303 → 「开启」
③ sha256Hex(input) === DEV_PASSWORD_HASH ?
     否 → 行内红字「口令不符」（不写任何状态、不写日志）
     是 → sessionStorage 写 token；state.settings.devMode = true
          pushLog(state, '开发者模式已开启：已解锁资源无限。', 'warn', 'dev:on')
④ 立刻渲染一次状态条（不等下一个 tick）

【生效】
⑤ 每个 tick 末尾：tick() 里 simulateSpan/advanceCaravans/checkMilestones 之后 → devRefill(state)
⑥ 离线段末尾：runOffline() 里 advanceCaravans 之后、return 之前 → devRefill(state)（口径与在线一致）
⑦ 消耗照常发生（兑丹扣 1 灵石 → 下一 tick 回满）⇒ 玩家看到的是「无限」，而不是「数字不动」
   ⚠ 这条是刻意的：扣减点一处都不改，所以「答错地狱难度没收材料」等既有惩罚**行为不变**

【关闭】
⑧ 设置行按钮变「关闭」→ 清 sessionStorage token、state.settings.devMode = false
   → pushLog(state, '开发者模式已关闭。', 'info', 'dev:off')
⑨ 关闭后**已经补出来的量留在那里**（不回滚、不追溯）——
   理由：回滚要靠「记住开启前的值」，那是第二个真相源，而且会让「我关掉之后钱没了」变成 bug 报告
⑩ 刷新 / 重开标签页：token 失效 ⇒ 即便存档里 devMode 仍是 true，devRefill 也不生效；
   界面会显示「已开启（需重新验证）」并要求重新输口令（或点「关闭」把它彻底关掉）
```

### 5.4 界面：怎么显示「开发者模式已开启」

| 位置 | 元素 id | 内容 |
|---|---|---|
| 设置面板新增一行 | `#dev-mode-row` | 未开启：`开发者模式` + 按钮「开启」；已开启：**`⚑ 开发者模式已开启`** + 按钮「关闭」 |

**「绝不能误伤正常玩家」的四道闸**（t4 逐条验，见 §九）：

1. `createState().settings.devMode === false`（**开局就是关的**）。
2. 旧存档（`raw.settings` 完全没有 `devMode`）`hydrate` 后 `=== false`。
3. `devModeOn()` 要求 **token + 开关同时为真** ⇒ 手改存档不足以开启。
4. `devRefill()` 在 `devModeOn() === false` 时**第一行就 return** ⇒ 不开模式时它对状态的写入次数恒为 **0**（可以用「序列化前后逐字段相等」来验）。
