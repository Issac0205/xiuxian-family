## 一、测试方法论与证据分级（先讲清每条结论的可信度）

本报告每条结论都标注证据等级，禁止用「测试过了」代替证据：

| 级 | 含义 | 本轮用法 |
|---|---|---|
| **L1 解析** | 从速率常量直接算，不跑仿真 | 「挂机多久才够」类全部走 L1（T-0 供给、T-3 收益比、T-4 速率、T-6 期望丹纹） |
| **L2 注入** | 把状态设到门槛上，立刻调用动作并断言 | 功能正确性（T-1 白名单、两侧门槛、T-2 状态机、T-5/T-6 结算、T-1 真刷新） |
| **L3 定点短推** | 只推「一个特征时间」，并说明为什么不能解析求解 | 仅 2 处：走火速率的两侧边界（推 1 秒 = 该速率的定义周期）、散功冷却（推 600 秒验证挡住） |
| **L4 全流程** | `scripts/balance.mjs` | **只用来验整体节奏，不作为功能正确性证据**（见 §二） |

**L3 的两处为什么不能解析：**

1. **走火判定**是随机过程（`rng() < 1 − e^{−λ·dt}`，`src/systems/cultivation.js:400-416`），
   无法解析求解「这一次会不会触发」，只能注入骰子门控。
   推 **1 秒**不是「大概够长」，而是**该速率的定义周期**（`PUSH_FIRE_PER_LOCAL = 1.0e-4/秒`，
   `src/core/config.js:140`）。两侧用 `λ·(1∓1e-6)` 的骰子夹逼，等于反解出 λ 的区间：
   实测 `local=3` 与 `local=9` 都能把速率夹在 `local×1.0e-4` 上（下方 §三 T-3 ③）。
2. **散功冷却**是 `stalled` 的线性递减，本来可解析；这里推 600 秒只是**顺带证伪**——
   若冷却没挡住修为，600 秒足够涨出可见的 xp。它不是数值结论的来源。

**L4 的定位与标定（照要求披露耗时）：**
`scripts/balance.mjs --hours 1 greedy` 实跑 **8.0 秒 / 游戏小时 / 策略**（进程层单条），
即 40 小时单条约 **5.3 分钟**、三条策略并行约 5～6 分钟。
本轮**没有**跑 40 小时仿真：`docs/91 §10.4` 已把 T-0 验收①的「40 小时 clues ≥ 20」改成解析估算，
我沿用该口径（§三 T-0 ① 写明），L4 只跑到 2 小时看整体节奏与「秘闻池何时被吃干」。

**T-3 数值结论（L1 解析，公式、常量与出处）：**

| local | N | m（期望走火） | E[T_猛进]/T_缓修 |
|---|---|---|---|
| 1 | 45 | 0.002 | ×0.455 |
| 3 | 405 | 0.055 | ×0.437 |
| 5 | 1125 | 0.256 | ×0.393 |
| 8 | 2880 | 1.047 | ×0.803 |
| **9** | 3645 | **1.491** | **×1.049（比缓修慢 4.9%）** |

## 七、我自己的教训（方法学，已上报监管者）

1. **`confirm()` 会让 headless 浏览器永久卡住，表现是「探针一行结果都回不来」。**
   真浏览器里点「投帖 / 结丹 / 散功 / 召回 / 冲关」这些按钮全都会走 `confirm()`，
   而 headless 没有人去点那个对话框 ⇒ renderer 阻塞。
   **修法**：探针先把 `window.confirm`/`alert` 换成自动确认（垫片里也需要 —— `installDOM` 只把它挂在
   `window` 对象上，**没有设 `globalThis.confirm`**，所以 `src/main.js` 里的裸 `confirm(...)` 在垫片里会 ReferenceError）。
   我为此浪费了 5 次以上的「超时」排查，**先做最小复现页面**（十几行 HTML + `fetch`）才分清是环境问题还是被测对象的问题。
2. **`--dump-dom` 会挂起，改用「本地 HTTP 服务 + 页面 `fetch('/r')` 回传」。**
   这个自建回传通道是本次最有用的一件工具：不依赖 CDP，也不依赖 `--virtual-time-budget`。
3. **垫片与浏览器有三处语义差，跨过它们就会得到假结论**：
   ① 垫片不计算可见性（主策已指出）；
   ② `el.hidden = false` 在浏览器里会**摘掉属性**，垫片里属性会留下 ⇒ 只按 `hasAttribute` 判会得到假阳性（我第一版就中了，靠第三重对照才发现）；
   ③ `matchesSelector()` 不支持逗号选择器、没有 `select.value`、`appendChild` 不先从旧父摘除、`insertBefore` 未实现。
4. **PowerShell `>` 重定向产物是 UTF-16**，node 按 utf8 读会把 `✓/✗` 读成乱码、计数得 0
   ⇒ 所有计数都用 `2>&1 | Set-Content -Encoding UTF8` 落盘后再用 node 统计（与 `~/.dsh/rules` 的 R7 同源）。
5. **一条「通过」的断言必须能说得清「它凭什么会失败」。** 本次最典型的一次自我翻车：
   我第一版「丹纹带到元婴期」的检查拿 `marks=1` 与 `marks=13` 在元婴期比，得到比值 **0.8065 ≈ 0.80**，
   **看起来完美命中「−20%」**。实际上那只是丹品修炼倍率本身（九品 1.00 vs 四品 1.24 = 0.806）在作怪 ——
   这条修正在实现里**根本不存在**。改成「同一个 marks 在元婴/金丹之间比」后立刻露出真相（1.0000）。
   **凡是「算出来正好等于期望值」的检查，都要问一句：它是不是在量别的东西？**
6. **别把猜测写成结论。** 我一度认定残留的 Cloudflare beacon「会挡住 module 脚本」
   （因为它确实让 `--dump-dom` 挂起过）；实测 `keep` / `strip` 两组对照后发现**不阻塞**，真凶另有其人（见教训 1）。
   证据不足时我把它降级为「低优先级瑕疵」，没有写进缺陷清单的主干。
