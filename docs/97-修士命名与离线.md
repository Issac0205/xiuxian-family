## 零、这份文档回答什么

用户原话三条（逐字）：

> 「我之前有修士名册系统，现在我希望能改进命名策略，之前出来的所有修士全是什么什么清衡一点代入感都没有。」
> 「除了优化修士名册以外，我还希望能够增加给特定修士命名的规则，这样可以专门培养自己喜欢的修士。」
> 「还有我希望退出游戏的时候回来不要给太多收益，比如我有一次结束游戏，回来发现多了两百个修士，我一下子不想玩了。」

把三条读成一句：**家人该像人，而不像一个数字。**
想要**认识**自己的修士（命名）→ 想要**挑出**在意的修士（赐名）→ 不想回来被**陌生人淹没**（离线收敛）。

本文按这三段给出可实现的规格，每条数值结论都标了级别（L1 解析 / L2 状态注入）与常量出处（`文件:行号`）。

## 一、现状诊断（不是感觉，是量出来的）

### 1.1 命名：**不是池子小，是索引顺序**

`src/systems/cultivation.js:7-8`：
```js
const CULTIVATOR_SURNAMES = ['林','顾','沈','陆','苏','谢','秦','周','许','叶','唐','白'];   // 12
const CULTIVATOR_GIVEN    = ['清衡','云岚','知微','怀瑾','望舒','玄澈','清越','景行','思远','若虚','静尘','长风']; // 12
```

`src/systems/cultivation.js:152-155`：
```js
function cultivateName(id) {
  const i = Math.max(1, Math.floor(id)) - 1;
  return CULTIVATOR_SURNAMES[i % 12] + CULTIVATOR_GIVEN[Math.floor(i / 12) % 12];
}
```

**它是「先把 12 个姓用完，再换下一个名」**（L1 解析 + L2 实测）：

| id | 生成名 |
|---|---|
| 1 | 林清衡 |
| 2 | 顾清衡 |
| … | … |
| 12 | 白清衡 |
| 13 | 林云岚 |
| 145 | 林清衡（与 id=1 完全相同）|

L2 实测（探针输出 `firstSixNames` / `name1` / `name145`）：
```
firstSixNames = ["林清衡","顾清衡","沈清衡","陆清衡","苏清衡","谢清衡"]
name1   = "林清衡"
name145 = "林清衡"
```

**⇒ 每一批连续 12 名修士共用一个「名」。开局第一批恰好是 id 1–12，于是开局 12 个修士全部叫「×清衡」。**
用户说的「全是什么什么清衡」不是池子小（144 个组合并不算少），而是**索引顺序把同一批人排成了同一个名**。池子再大，只要还是这个顺序，前 12 个人照样同一个名。

**全族 300 人时到底有几个同名（确定性，不是概率）：**

名字空间 = 12 × 12 = 144，而生成方式是**轮转**（id 连续），所以分布是确定的：

- id 1–288（288 人）：144 个全名**各出现 2 次**（id 与 id+144 撞名）
- id 289–300（12 人）：落到 id 1–12 那 12 个全名上，于是**这 12 个全名各出现 3 次**

| 指标（N = 300） | 值 |
|---|---|
| 出现的不同全名数 | 144 |
| 132 个全名各 | 2 人 |
| 12 个全名各 | 3 人 |
| **重名对数** Σ C(nᵢ,2) | **168 对** |
| 与别人同名的人数 | 300 − 144 = **156 人（52%）** |
| 同名的最大人数 | **3**（如「林清衡」）|
| 对照：若改成随机分配（生日问题 C(N,2)/M）| C(300,2)/144 = **311 对**（现状的轮转反而"整齐"一些，但同样必然重名）|

名册上限 `CULTIVATOR_LIMIT = 300`（`cultivation.js:6`）+ 仙道科技 **+650**（`immortalCapFlat` 合计，L2 实测 `immortalCapFlat_allTechs = 650`）⇒ **满配名册 950 人**。950 人铺在 144 个名字上 = 每个名字 6.6 人。

### 1.2 离线：+200 人的真凶是「天降灵根」

**三条产出修士的通道**（全部在离线路径上）：

| 通道 | 出处 | 速率公式 |
|---|---|---|
| **A 天降灵根**（主凶）| `src/systems/cultivation.js:338-349` | `E = 出生数 × INNATE_CHANCE_PER_BIRTH × innateMult × min(5, 在世修士数/10)` |
| B 修士婚育 | `src/systems/cultivation.js:350-353` | `floor(N/2)/3e6` 人/秒 = `floor(N/2) × 0.0012` 人/游戏小时 |
| C 灵池 | `src/systems/immortal-economy.js:23-33` | `pool/4800` 人/秒 × `operating`（受灵石预算限制）|

常量出处：
- `INNATE_CHANCE_PER_BIRTH = 0.0000125`（八万分之一）— `src/data/cultivators.js:52`
- `innateMult = 1 + fxTech.innateBirthMult + innatePoolBonus(state)` — `cultivation.js:345`；`innatePoolBonus = min(1.2, pool×0.12)` — `cultivation.js:205-208` + `config.js:254-255`
- 仙道科技 `innateBirthMult` 合计 **+2.15**（4 项：`immortal-techs.js:73` 0.6 / `:113` 0.9 / `:216` 0.35 / `:307` 0.30，L2 实测 `innateBirthMult_allTechs = 2.15`）⇒ `innateMult` 上限 **1 + 2.15 + 1.2 = 4.35**
- 灵池上限 **10 座** — `src/systems/immortal-actions.js:17`（`if(c.pool>=10)return fail('灵池已达上限')`）+ `save.js:207`（`Math.min(10, …)`）⇒ 通道 C 上限 **10/4800 = 7.5 人/游戏小时 = 90 人/12 小时**
- 离线上限 `OFFLINE_CAP_HOURS = 12` — `src/core/config.js:31`；推进在 `src/core/engine.js:841-864 runOffline()`

**人口为什么会是 10⁵ 级**：`src/core/engine.js:743-754` 里 `births = population × derive.birthRate × dt`，而 `derive.birthRate = (0.010 + 科技 + 田地×0.0012×(1+田地加成)) × 流派倍率`（`src/core/formulas.js:354-356`），`deathRate` 由拥挤项 `0.014·crowdOver²` 封顶（`formulas.js:366`）。于是人口收敛到一个**平衡点 P\***，而不是无限增长——但出生流量是 `P* × birthRate`，中期就是**十万婴儿/游戏小时**级。

**⇒ 挂机 12 小时 = 一百多万次生育 × 八万分之一 × 4.35 × 5 ≈ 400+ 人。** 不是 bug，是"时间直接乘在人口级的出生数上"。

### 1.4 顺手挖出的一个**会静默毁档**的坑（与命名直接相关）

- `serialize()` 写的是 `cultivation: state.cultivation` **整块**（`src/core/save.js:11-48`）——所以新加的逐人字段**写得进**。
- 但 `hydrate()` 重建修士时是**逐人字段白名单**：`src/core/save.js:187`（正常路径）与 `:199`（老存档只有 `qi` 整数的路径），
  ```js
  fresh.cultivation.cultivators.push({ id, name: cultivateName(id), origin, root, realmIndex, xp,
    breakFailures, talent, job, parentage, push, stalled, realmEnteredYear, foundation, core });
  ```
- **⇒ 任何没被搬进这两行的新字段，读档后都会由 `ensurePersonFields()`（`cultivation.js:50-91`）重置为默认值。**
  玩家的赐名会**不报错、不崩溃地消失**——这与全局规则 `save-compatibility.md` R2 里 `meta` 字段那次事故是同一类，只是从"顶层白名单"下沉到了"逐人白名单"。
- 同一处还有第二条：`name: cultivateName(id)` 是**每次读档重算**的。新命名方案必须保证「名字能由 (id, joinedYear, 同代序号) 重算」，否则读档后名字会变。
- `SAVE_VERSION`（`config.js:189`）**只写不校验**（`hydrate` 里没有任何 `raw.version` 判断，L1 全仓 grep 确认），所以版本号帮不上迁移的忙——迁移只能靠字段自身的形状判定。

## 二、命名系统设计

### 2.1 结构：姓 + 字辈 + 名（三段四字）

现名是「姓 + 双字名」= 3 字。新名是「**姓 + 字辈 + 双字名**」= **4 字**，例：`林玄承渊`、`顾绍观澜`。

- **姓**：家族分支。24 条。
- **字辈**：**按世代推进**——同一代全族共用同一个字辈字。这是"世家"最直接的视觉：一眼看出「玄字辈」「绍字辈」。
- **名**：个人区分。97 条（**质数**，见 2.3 的零重名构造）。

**姓池 `SURNAMES`：24 条**（前 12 条是现有词表，一条不动；后 12 条为新增）

卫 韩 崔 裴 邵 温 岑 商 燕 骆 詹 屠

风格口径：水墨 + 器物 + 节气 + 山川，全部守本项目的气质（**没有**「张伟」「李娜」这类现代日常名，也没有「王小明」式的现代双字）。

**世代怎么算**：`gen = floor(joinedYear / GENERATION_YEARS)`，`GENERATION_YEARS = YEARS_PER_GAME_HOUR = 25`（`src/data/realms.js:123`）。
⇒ **一代 = 1 游戏小时 = 25 年**。一周目 44.6 游戏小时 ≈ 45 代，与"寿元钟 1 h = 25 年"（`engine.js:824`）**同一把尺子**，玩家在族谱上看到的年限与字辈是同构的。

### 2.3 生成算法（确定性 + 零重名）

```
gen = floor(p.joinedYear / 25)          // 世代序号
k   = 该修士在「同 gen」内按 id 升序的序号（0 起）
name = SURNAMES[k % 24] + GENERATION_CHARS[gen % 64] + GIVEN[k % 97]
```

**为什么名池取质数 97 而不是 96**：
两个人在同一代内全名相同 ⟺ `k ≡ k' (mod 24)` 且 `k ≡ k' (mod 97)`。
`gcd(24, 97) = 1` ⇒ `lcm(24, 97) = 2328` ⇒ **同一代内前 2328 人零重名**。

- 若名池取 96：`lcm(24,96) = 96` ⇒ 同代第 97 人与第 1 人撞名，**而且会撞成「姓也相同」**，等于把现在的 bug 换个位置复现。**所以质数是必需的，不是讲究。**
- 单代实际人数上限：中期城在线全科技约 **34 人/游戏小时**、后期大城约 **105 人/游戏小时**（由 1.2 的模型算；S3 的出生 388,173/时 × 4.35 × 1.25e-5 × min(5,·) = 105）。**2328 是它的 22 倍。**

**跨代重名**：字辈不同 ⇒ 全名必不同。字辈表 64 条，`gen ≥ 64`（= 64 游戏小时）才回绕，而一周目 44.6 游戏小时。⇒ 一周目内**跨代也不会撞**。

**⇒ 全族 300 人时同名 0 个。全族 950 人（满配）时同名 0 个。**

### 2.4 重名概率对照表

| 方案 | 名字空间 | N = 300 的重名对数 | 最坏同名人数 |
|---|---|---|---|
| **现状**（12×12 轮转）| 144 | **168**（确定性）| **3** |
| 现状若改随机分配 | 144 | 311（期望）| ~5 |
| **新方案**（24×64×97 = 148,992，按 2.3 构造）| 148,992 | **0**（构造保证）| **1** |
| 新方案若退化为纯随机分配（不给构造，只给池子）| 148,992 | C(300,2)/148,992 ≈ **0.30**（至少一对同名的概率 ≈ 26%）| 2 |

**⇒ 结论一句话：池子扩到 14.9 万只能把 300 人撞名从「必然」降到「26% 概率撞 1 对」；真正把重名压到 0 的是 2.3 那个「同代内 `k` 唯一 + 名池取质数」的构造。** 只换词表不换算法，等于换个池子继续轮转。

### 2.5 读档稳定性（硬要求）

名字必须能**由存档里的既有字段重算出来**，否则 `save.js:187/199` 每次读档重算 `name` 会让玩家的修士改名。

- 用到的输入只有 `p.id` 与 `p.joinedYear`（新字段，见 3.2）——**两者都在存档里**。
- `k`（同代序号）必须在**全量排序后**统一重算，不能边 hydrate 边算（数组顺序不可信）。
  - 新增 `refreshGenerations(state)`（幂等）：按 `id` 升序扫一遍 `cultivators`，用 `Map<gen, count>` 计出每人 `gen`/`k`，写入**派生字段** `p._gen` / `p._k` / `p.name`。
  - 调用点：`repairCultivation()` 末尾（`cultivation.js:104-151`）、`addCultivator()` 之后（只需给新人算，因为 id 最大 ⇒ `k` 只增）。
  - ⚠ **`p._gen` / `p._k` 是派生字段，绝不落档**（`save.js:187/199` 的白名单里不要加，也不要在 `serialize` 里出现）。否则存档里有两份真相。
- 复杂度：N ≤ 950 ⇒ 一次全量重算 ≈ 45 万次比较，**毫秒级**；但**不要放进每帧 `render()`**。

**老存档的名字迁移**（必做，否则老玩家认不出自己的修士，却不给任何提示）：

- 判据用**名字长度**：老池生成的是 3 字（1 姓 + 2 名），新池生成的是 4 字（1 姓 + 1 字辈 + 2 名）。
- 规则：`p.name` 已存在且 `Array.from(p.name).length !== 3` ⇒ **保留原 `p.name`**（视为玩家/异常数据）；长度 === 3 ⇒ 判定为旧池 ⇒ 换成新四字名。
- 注意：玩家的自定义名在 `p.title` 里，**不参与**这个判定（`p.name` 永远是系统名）。
- ⚠ `SAVE_VERSION` 帮不上忙（只写不校验，见 1.4），所以只能靠形状判定。**这一点在 `save.js` 里要写注释说明原因**，否则后人会以为用版本号更干净而来"优化"掉它。

## 三、指定命名（赐名）

> 定位：这是「**专门培养自己喜欢的修士**」的抓手，也是"依恋"的落点。
> **硬边界：赐名只改显示名，不改任何数值**——不改战力、不改修炼速度、不改突破率、不改寿元。一旦掺进数值，它就从"人情"变成"氪金位"，并且会和 `docs/00-整体策划.md` 的"数字要能被玩家算出"打架。

### 3.1 何时可用

| 情形 | 规则 |
|---|---|
| **首次赐名**（每名修士一次）| **免费**。这是"我认识他"的入口，不该有价格门槛。 |

## 四、离线收益收敛

### 4.1 三条通道与公式（复核用）

```
通道 A（cultivation.js:338-349）
  eventChance = 1 - exp( -births × INNATE_CHANCE_PER_BIRTH × innateMult × min(5, N/10) )
通道 B（cultivation.js:350-353）
  pairChance  = 1 - exp( -floor(N/2) × dt / 3000000 )
通道 C（immortal-economy.js:23-33）
  cost        = pool × 0.00013 × dt           // 灵石/秒，pool ≤ 10
  operating   = min(1, spiritStones / cost)
  chance      = 1 - exp( -pool × dt × operating / 4800 )
```

### 4.2 新口径：**离线只推凡人，不推仙缘**

> **一句话**：离线期间，人口、银两、作坊原料、灵矿出石、商队、领地赋税、修士修为增长**照常结算**；但「**新生一个修士**」这件事在离线期间**最多发生 1 次**。

具体：

1. **A / B / C 三条通道在离线结算期间受一个"觉醒预算"限制**：本次离线结算合计**最多产出 1 名修士**。
   - 机制上**不是"关掉"，是"截断"**：每步仍按原概率掷骰，只是累积产出达到 1 后，这三条通道**直接短路**（不再掷骰、不再消耗随机数，保持确定性）。
   - 于是「挂 30 秒刷新一次页面」**不构成刷人漏洞**：30 秒的期望产出 ≈ 0.067 人，概率门仍然把它挡住。
2. **灵池（通道 C）在离线期间既不产人，也不扣灵石**——否则就是"花了钱不产人"的纯亏。
3. `OFFLINE_CAP_HOURS = 12` **不动**；离线产出**不打折**；离线**永远不吃倍速**。
4. `runOffline()` 的返回值新增 `qiFrom / qiTo / qiGain`（`engine.js:855-863`），弹窗与族谱各加一行。

**为什么不是"打折"或"降上限"（做过的取舍）：**

| 候选 | 对 S2b（12h +490）的实际效果 | 判定 |
|---|---|---|
| 离线产出打 0.5× | 12h 变 6h 等效 ⇒ **+245** | ❌ 治不了，用户的痛点是"一口吞下的量"，不是"率" |
| `OFFLINE_CAP_HOURS` 12 → 4 | +490 → ~+160，但银两/原料/灵石**一起砍 2/3** | ❌ 误伤主线经济 |
| 人口相关产出自设更小上限（只夹通道 A）| +490 → 受上限约束（如 5），但通道 C 的 90 人没被夹住，而 C 与 A 会互相抬（`min(5, N/10)` 随 N 上升） | ❌ 治不干净，得夹两条 |
| **离线只推凡人（本文推荐）** | +490 → **+1** | ✅ |

**最关键的一条事实（它决定了上面的取舍）**：离线**没有"多给"**。S2 在线 1 游戏小时 = **+8**，离线 12 小时 = **+99** ≈ 12.4 × 8 —— **离线是如实结算的**。
所以这不是"奖励太肥"的问题，而是「**12 小时的仙缘被压成一次交付**」。正确的手术是**掐掉"新生"这一类事件在离线期间的结算**，而不是给它乘系数。
⇒ 副产品：这条改动把离线从"时间压缩包"重新定义成「**资源的托管 + 血脉的暂停**」，与用户那句"回来不要给太多收益"是同一种期待。

⇒ 真机理是**结构化偏置**：**边际分布与序列相关性同时坏掉**，命中率偏差**非单调**（p ≤ 0.75 偏高、p = 0.9 偏低）。实测该发生器的输出 `值 mod 512` 只取到极少数几个值。
