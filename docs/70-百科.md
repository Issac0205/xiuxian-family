## 一、这个区块解决什么问题

游戏到 R7 已经有五套子系统、二十多张数值表。玩家会问的问题有两类：

1. **「演武台到底是干什么的？为什么我的人一直在死？」**
2. **「炼气期是什么？为什么我要在意这个？」**

前者是**查数据**，后者是**要代入感**。这两类需求不该用同一种写法回答，
所以百科做的是**两层**：

| 层 | 作用 | 写法 |
|---|---|---|
| **志书**（prose） | 代入感，「这是个什么地方」 | 文言白话夹杂的短段落 |
| **数据引文**（lines） | 可查，「具体是多少」 | 从活表里生成的条目 |

目标里举的两个例子正好一边一个：

- 「演武场是对外征伐扩张，因此会死人」→ 志书层（取建筑自己的 `lore`）
- 「介绍炼气期等境界的背景知识」→ 志书层（R8 新写的五段）

## 二、最重要的设计决定：**聚合，不重抄**

前面七个区块里，背景文字早就写好了，而且**都写在数据表自己身上**：

| 来源 | 字段 | 谁写的 |
|---|---|---|
| 六类凡人建筑 | `BUILDINGS[].lore` | R1 |
| 八个地图节点 | `MAP_NODES[].lore` | R4 |
| 六个丹方 | `ALCHEMY_RECIPES[].desc` | R5 |
| 九件法器 | `FORGE_ITEMS[].desc` | R6 |
| 四张符箓 | `RUNE_ITEMS[].desc` | R7 |
| 五个大境界 | `REALM_TIERS[].desc` | R2 |
| 五档灵根 | `ROOT_GRADES[].desc` | R3 |
| 七种职责 | `CULTIVATOR_JOBS[].desc` | R1 |

所以 `data/codex.js` 里的绝大多数条目**不写新文字，只引用**：

```js
// 舆图章节：正文就是节点自己的 lore
entries: MAP_NODES.map((n) => ({
  id: `map-${n.id}`,
  title: n.name,
  prose: n.lore,          // ← 引用，不是复制
  lines: (s) => [...],    // ← 从活表生成
  seen:  (s) => mapAccessible(s, n.id),
})),
```

**为什么这件事重要**：如果百科另抄一份，那么以后改了地图节点的描述，
就会出现「地图上说是这样、百科里说是那样」——而这种不一致极难发现，
因为两处都不报错。

冒烟测试里有一整节（「百科：聚合而非重抄」）专门当这条约定的守门人：
它拿 `D.buildings` / `D.map` / `D.recipes` / `D.artifacts` / `D.runes` 里的原文
去比对百科条目的正文，**改表不改百科就会挂**。

## 四、数据引文：必须是函数

```js
lines: (s) => [ ... ]     // ← 函数，收到当前 state
```

**不能是静态字符串数组**。例如地图节点「青木寨」的引文里有这么一行：

```
占领后：3.6 灵石/时 + 青灵草 7.2/时 + 灵木 2.9/时 + 符纸 2.2/时
```

这四个数是 R4/R5/R6/R7 各自定义在 `MAP_NODES` 上的。
如果写成静态字符串，那么以后调产量，百科就会撒谎。

引文的另一个用途是**反映玩家的当前状态**：法器条目会写「当前耐久 34%」，
领地条目会写「当前状态：已占领」，宗门条目会按每个族人的资质算出引荐礼。

## 五、两条工程上的防御

百科是**只读的附属面板**，它绝对不能因为某一张表出问题就把整个页面搞崩。
所以两处都做了兜底：

```js
function codexEntrySeen(entry, state) {
  try { return Boolean(entry.seen ? entry.seen(state) : true); }
  catch (_e) { return false; }        // 判不出可见性 → 当作没解锁
}
function codexEntryLines(entry, state) {
  try { ... } catch (e) { return [`（数据引文暂不可用：${e.message}）`]; }
}
```

界面上看到的是「数据引文暂不可用：xxx」，而不是白屏。冒烟测试里有一条
专门喂一条会抛错的条目定义来验证这个兜底。

## 六、搜索：覆盖正文，不只是标题

目标里那条需求（「演武场是对外征伐扩张，因此会死人」）的实现方式就是搜索：

> 玩家记得「死亡率」三个字，但想不起是哪个建筑的 —— 搜「死亡率」，
> 演武台的条目就会出来。

搜索的是**四处并集**：`标题 + 正文 + 数据引文 + 标签`。
并且**只搜已解锁的条目**，不然就是剧透。

标签是给这类模糊记忆准备的补充入口：地图条目带「洞天 探险」「势力 攻伐 占领」，
丹药带「炼丹 丹药」，法器带「炼器 兵器」。

## 七、界面

- **独立页签**（目标要求「单开一个栏目」）：顶栏第六个 tab「百科」，
  移动端底部导航也补了图标。
- **未解锁的条目占位**：显示为「？？？」加一句解锁提示（「打通相邻的地区后可见」）。
  这比直接隐藏好——玩家知道还有东西没见到，但不剧透。
- **搜索时不再显示占位**，只列命中的条目。
- **脏检查**：签名是「各章可见条数 + 搜索词 + 当前章节」，
  所以每秒的定时刷新不会重画整个列表。

## 八、新增的数据层调试出口

写测试时发现 `BUILDINGS` 这些表在 `new Function` 的闭包里，
测试拿不到。于是加了：

```js
__xiuxian.data = {
  buildings, techs, map, realms, gates, roots,
  herbs, recipes, furnace, ores, artifacts, smithLevels,
  runeMats, runes, benchLevels, jobs, daos, manuals, chapters,
}
```

这本身就有价值——现在可以在控制台里直接 `__xiuxian.data.recipes` 核对数值，
不必再去翻源码。**百科把自己逼出来的这个出口，顺便解决了整个项目的一个调试盲区。**
