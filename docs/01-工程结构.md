# 工程结构与区块约定

> 配套文档：`00-整体策划.md`（做什么）、本文（怎么放代码）。

---

## 一、为什么要分区块

拆分之前是一个 **9500 行、15 个「伪模块」** 的单文件：
模块靠注释分隔，没有 `import/export`，所有声明挤在同一个顶层作用域里。

再加炼丹／炼器／炼符／地图／百科／周目，会破两万行——那时候改一个数值要在
两万行里找，加一个功能要担心撞名，两个人不能同时改。

**所以拆成「一块一文件」，构建时再合成单文件产物。**
玩家拿到的仍然是一个双击即玩的 HTML，开发时面对的是一堆小文件。

## 三、日常怎么改

```powershell
$node = 'C:\Users\issac\.dsh\dsh-runtimes\dsh-primary-runtime\dependencies\node\bin\node.exe'

# 改完 src/ 下的文件，合成产物
& $node scripts/build.mjs

# 跑测试（会重新加载 game.html）
& $node scripts/smoke.mjs

# 只想知道产物是不是最新的
& $node scripts/build.mjs --check
```

**永远不要直接改 `game.html`** —— 它是产物，下次 `build.mjs` 就覆盖了。
（`extract.mjs` 只在最初拆分时跑过一次，之后不需要。）

## 四、加一个新区块

以「炼丹」为例，目标是新增两个文件：

```
src/data/alchemy.js        # 灵药表、丹方表、数值常量
src/systems/alchemy.js     # 采集、炼丹、熟练度、结算
```

步骤：

1. **建文件**，开头写区块头注释（见 §五）。
2. **往 `src/_manifest.json` 里插一条**，位置决定拼接顺序：

   ```json
   { "path": "src/data/alchemy.js",    "marker": "/* ══════════ src/data/alchemy.js ══════════ */" },
   { "path": "src/systems/alchemy.js", "marker": "/* ══════════ src/systems/alchemy.js ══════════ */" }
   ```

3. **`build.mjs`** —— 产物里就多了这一段。

### ⚠️ 拼接顺序就是执行顺序

所有区块**共享同一个顶层作用域**（没有模块系统）。所以：

- **`const` / `let` 必须在被使用之前出现**（否则运行时 TDZ 报错）。
  依赖别人的常量，就把自己的条目排在它后面。
- **顶层名字必须全局唯一**。两个区块各写一个 `const CONFIG` 会直接
  让整个 `<script type="module">` 语法错误、白屏。
  加新名字前先搜一遍：`Select-String -Path src/**/*.js -Pattern 'const 名字'`。
- 函数声明会提升，但**函数体内引用的 `const` 仍受顺序约束**——
  只要函数是在初始化之后才被调用，就没问题。

### 依赖方向

```
ui  →  systems  →  data  →  core
```

**只能向上依赖，不能向下。** 跨区块一律调 `systems/` 暴露的函数，
不要直接读别的区块的 `data`。

## 五、区块头注释约定

每个文件开头都要有一个「这一块管什么」的注释框。`extract.mjs` 自动生成的格式：

```js
/* ────────────────────────────────────────────────────────────────
 * 区块：功法表：道途 / 品阶 / 十五本 / 参悟调参常量
 * 原属 src/data/cultivation.js 第 39–110 行
 * ──────────────────────────────────────────────────────────────── */
```

新写的区块用这个格式：

```js
/* ────────────────────────────────────────────────────────────────
 * 区块：炼丹
 * 职责：灵药与丹方的数据表 + 炼丹结算规则
 * 依赖：data/manuals.js（火种来自炼器）、systems/exploration.js（灵药来自地图）
 * 调参：本文件顶部三个常量是唯一旋钮，改这里不需要动 systems/alchemy.js
 * 文档：docs/30-炼丹.md
 * ──────────────────────────────────────────────────────────────── */
```

**必须写清四件事**：管什么、依赖谁、数值旋钮在哪、对应哪份文档。
这样下一个人（或下一轮的我）不用读完代码就能定位。

## 六、数值与逻辑分离

这是「方便后续调整」的核心要求：

| 层 | 放什么 | 改它会影响 |
|---|---|---|
| `data/*.js` | 表、常量、文案 | 数值平衡，不影响流程 |
| `systems/*.js` | 读表 → 计算 → 改 state | 流程与规则 |
| `ui/*.js` | 把 state 画出来 + 发意图 | 排版与交互 |

**硬性要求**：

1. `data/` 里不出现 `if`。表就是表，条件判断属于 `systems/`。
2. `systems/` 里不出现魔法数字。要调的数值一律提到文件顶部常量区或 `data/` 的表里。
3. `ui/` 里不做玩法判定。它只读 `derive(state)` 的结果和 `systems/` 暴露的
   `planXxx()`（后者负责说明「这个操作能不能做、代价多少」）。

## 七、拆分的可靠性是怎么保证的

拆分是**机械的、可验证的**，不是重写：

1. `extract.mjs` 从产物里切出模块后，**立刻拼回去比对**——
   逐字节一致才继续，否则报出第一个差异位置并退出。
   首次拆分的结果：**✓ 逐字节还原成功**。
2. 把 `data/cultivation.js` 切成 9 个文件时，用的是**连续的、覆盖每一行的
   行区间**，所以按新顺序拼回来必然与原文件等价，
   只多出 9 个区块头注释框。
3. 拆分后做了一次差异核对：**「删除行里不是标记/空行的」= 0，
   「新增行里不是标记/区块头/空行的」= 0**。
   也就是说代码一个字都没动。
4. 最后跑 `smoke.mjs`：**100 项断言全过**。

以后每次改动都走同一条流水线：`build.mjs` → `smoke.mjs`。
