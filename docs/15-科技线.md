# 科技线：凡人城市 × 仙道参悟

> 本文是两个系统的**唯一权威说明**：凡人侧「格物」与仙道侧「参悟」。
> 它同时是调参手册 —— 改数值之前先读第三节的反馈循环，改完之后跑
> `scripts/balance.mjs` 与 `scripts/diagnose.mjs` 对照第五节的口径。

- 数据：`src/data/techs.js`（凡人，18 项）、`src/data/immortal-techs.js`（仙道，23 项）
- 结算：`src/core/formulas.js` 的 `techEffects()` / `derive()` / `cultivationEffects()`
- 门槛：`src/core/config.js` 的「仙凡经济」一节
- 文档版本：v2（本版新增仙道线、城坊建筑、递进兑率）

---

## 一、设计支柱

这四条是**不可妥协**的。后面每一个数值决策都拿它们当尺子。

1. **数字稳稳长大**：挂机游戏的黄金感受是「离线回来又厚了一层」。
   任何互相依赖都不能表现为「等对面解锁」。
2. **每阶段有明确的下一步**：任一时刻玩家至少有一项「现在就能做、且值得做」的事。
   反例是一堆点了只为它自己的孤儿节点（v1 的 6 个孤儿就是这个问题）。
3. **依赖是双向的，但有方向**：主线永远是 **凡人 → 仙道** 单向流动
   （城养仙，不可逆）。反向（仙 → 凡）只出现在**可选深处**，
   而且必须给的是「更多」而不是「许可」。
4. **两条线各有自己的货币与手感**：凡人线是「银两、人口、营造，慢慢铺开」；
   仙道线是「灵石、修士、境界，一层层往上涨」。混在一起就两边都不像。

### 支柱 3 是踩坑换来的

第一版让「祛障」（凡人篇最后一道门）require 仙道的「引灵」，
用意很好 ——「城要养得起修士，先得把灵气往族里引」。
实测结果是**互相卡脖子**：只要仙道侧不可用，祛障就永久锁死 →
没有修士 → 仙道永远开不了 → 祛障永远开不了。整条主线停死。

现在的硬规则写在 `src/data/techs.js` 的头部注释里：

> **跨树前置只能挂在凡人线的可选深处，绝不能挂在主线上。**
>
> 允许：义庄 ← 悬壶、集贤馆 ← 聚灵阵、仙凡互市 ← 界墟（都是 tier 6–7）
> 禁止：任何 tier 1–5 的凡人科技依赖仙道

对应回归测试在 `scripts/smoke.mjs`：
「主线科技『祛障』在仙道侧为空时也可研习（无软锁）」。

## 二、两条线各自的主轴

| | 凡人城市线（格物） | 仙道线（参悟） |
|---|---|---|
| 货币 | 银两 | 灵石 **+** 银两（双付） |
| 载体 | 建筑与人口 | 修士与境界 |
| 主轴 | **把城做大**：人口 → 银两 → 营造 → 更大的城 | **把人炼上去**：灵石 → 境界 → 战力 → 更多灵石 |
| 上限 | 人口、银两上限、营造格位 | 名册容量、镇守战力、冲关成功率 |
| 负面对价 | 死亡率（拥挤 / 做工 / 走出去的人回不来） | 修士阵亡与叛离（洞天、攻伐、民怨） |
| 玩家在想什么 | 「这一笔钱盖什么最划算」 | 「这个人现在该冲关还是再攒一枚丹」 |

### 凡人城市线的三个阶段

- **立族 · 兴家 · 拓土（T1–T3）**：把地基铺开。房地产 → 建筑学/金融 →
  营造术/对外扩张。这一段是一局里最"顺"的部分，几乎不给负面对价。
- **通商 · 致远（T4–T5）**：第一次真正的取舍。探秘者拿收入和命换消息，
  屯田换人口，算学换银两率，驿道换商队速度。
- **祛障 · 望郡（T6–T7）**：门开了之后怎么把根扎在城里。
  这一段新增的节点全是「为仙道服务」的：坊市扩建（兑率）、义庄（减死亡）、
  集贤馆（自主寻秘）、乡贤祠与仙凡互市（城市终局）。

### 仙道线的五个阶段

| 阶 | 名字 | 这一段在解决什么 | 关键节点 |
|---|---|---|---|
| 一 | 开脉 | 破障之后，先要**养得住人** | 开脉（名册 +150）、引灵（天生灵根 +60%） |
| 二 | 筑基 | 立起根基，方谈攻守 | 筑基之道（冲关 +6pp）、镇岳（镇守门槛 −30%）、丹药房 |
| 三 | 结丹 | 一丹既成，术法始有锋芒 | 御剑术、悬壶、聚灵阵、金丹大道、福地、探穴 |
| 四 | 元婴 | 神通离体，山川皆可往来 | 洞府（洞天 +6pp）、灵脉感应（开矿场） |
| 五 | 化神 | 化神之后，族与城都不必再分开算 | 元婴大道、灵田术、九转丹房、周天搬运、界墟、化神大道、结庐 |

### 与 v1 的差别：孤儿清零

v1 有 6 个孤儿节点（`surveying` `tuntian` `seeker` `arithmetic` `courier` `quzhang`），
点了只为它自己。v2 的规则是：**每一项科技都必须被另一项 require，
除非它带 `terminal: true`（该条线刻意的最后一块碑）**。

```
$ node scripts/balance.mjs --baseline | grep 孤儿节点合计
   孤儿节点合计：0 个      # 凡人侧
   孤儿节点合计：0 个      # 仙道侧
```

除 `xiangxian` / `mutualmarket` / `jielu` 三个终局节点外，全部有后继。

## 三、仙凡如何相互依赖（本设计的灵魂）

### 3.1 六处硬咬合（数据里的 requires / requiresImmortal）

| 方向 | 上游 | 下游 | 为什么 |
|---|---|---|---|
| 凡 → 仙 | 屯田 | 仙道「灵田」 | 屯田的法子搬到灵田上用，引灵台的水先浇过一遍 |
| 凡 → 仙 | 探秘者 | 仙道「灵脉感应」 | 找矿脉是凡人打听出来的风声，寻龙尺只是凡器 |
| 仙 → 凡 | 引灵 | 屯田 | 灵气引到田里，屯田才真的能多养人 |
| 仙 → 凡 | 悬壶 | 义庄 | 悬壶堂的药先紧着老人孩子，死的人少了才敢多生 |
| 仙 → 凡 | 聚灵阵 | 集贤馆 | 馆里养的是替仙家记档递帖子的人，顺带带回山外的消息 |
| 仙 → 凡 | 界墟 | 仙凡互市 | 城里想开一条两边通用的街，先得对面认你的字号 |

前两条在**仙道侧的数据表**里（仙道 require 凡人），后四条在凡人侧。
`node scripts/balance.mjs --baseline` 会把这六条逐条列出来。

### 3.2 软咬合（不写进 requires，但数值上互相喂）

这是更重要的一半 —— 它不锁任何东西，只是让「两条线都推」比「只推一条」划算。

```
                    │  人口 ──→ 银两 ──→ 营造 ──→ 更多的城 │

        ┌────────────────┘              │             └──────────────┐
        │ ①出生数                        │ ②银两换灵石                  │ ③城坊用工
        ▼                               ▼                            ▼
  天生灵根的孩子                    云深谷坊市                   药圃/矿寮/纸坊
  （INNATE_CHANCE_PER_BIRTH          （MARKET_EXCHANGE_*）         （CITY_*_PER_SEC）
   × innateBirthMult                 × (1 + tradeStoneMult)        × cityMaterialMult
   × innatePoolBonus）                     │                            │
        │                                  │                            │
        └──────────┐                       ▼                            ▼
                   ▼                  灵石 ──→ 参悟仙道科技        药材/矿料/符料
            更多修士 ─────────────────────┬──────────┘                 │
                   │                      │                          │
        ┌──────────┴──────────┐           ▼                          ▼
        │ ④镇守领地            │      境界 → 战力              丹药/法器/符箓
        ▼                      ▼           │                          │
   领地赋税（灵石）         攻伐 → 新领地   └──────────┬───────────────┘
   × territoryYieldMult                              │
        │                                            ▼
        └────────────────────────────→ 冲关门槛（石/线索/丹）→ 更高境界
                                                  │
                                                  ▼
                                        ⑤灵池：花灵石维持，
                                          提高天生灵根诞生率
                                          （回到 ①，闭环）
```

五条箭头的实体位置：

| # | 机制 | 实现位置 | 数值 |
|---|---|---|---|
| ① | 灵池与「引灵/灵枢」提高天生灵根诞生率 | `systems/cultivation.js`: `innatePoolBonus()`、`progressCultivators()` | `INNATE_POOL_BONUS_PER=0.12`，上限 +120% |
| ② | 城越大，银钱越值灵石 | `core/formulas.js`: `marketExchangeQuote()` | `tradeStoneMult` 由坊市扩建/仙凡互市/界墟/结庐给 |
| ③ | 城里的作坊把人口换成仙道原料 | `core/formulas.js`: `cityWorkersOf()`；`systems/immortal-economy.js`: `advanceCityWorkshops()` | `CITY_HERB_PER_SEC=0.0010` 等 |
| ④ | 领地赋税随仙道进度变厚 | `systems/exploration.js`: `mapYieldOf()` | `territoryYieldMult` 由洞府/周天搬运/结庐给 |
| ⑤ | 灵池把灵石变回好灵根 | `systems/immortal-economy.js` + `innatePoolBonus()` | 灵池耗 `pool×0.00013` 灵石/秒 |

### 3.3 张力的三个落点（有代价才有选择）

互相喂如果只有正反馈，就变成了「两条线都点满」的无脑最优解。
所以三处刻意留了**凡人对仙道的付出**：

1. **做工要死人**。药圃/矿寮/纸坊/坊市都要人，而人是共用的同一批：
   `cityWorkersOf()` 按人口分摊，人不够时所有作坊一起摊薄；
   同时每名用工每秒带走 `CITY_LABOR_DEATH = 0.0000001` 的死亡率。
   人口 2000、用工 1000 时约每秒 0.02 人（每小时 72 人）——
   而人口 2000 时的自然出生是每秒 22 人，所以它**咬得住、但咬不死**。

2. **矿工的命是凡人在填**。灵脉矿场的 `mineDeathMult` 由「引灵/灵枢」减负，
   但减不到零：`minWorkers × (0.0000025 + grade×0.000001)`。

3. **走出去的人回不来**。演武台与商队驿站的 `ARENA_DEATH` / `CARAVAN_DEATH`
   是 v1 就有的负面对价，保留不动 —— 它们与做工死亡叠加时，
   城市会进入「必须补田地」的状态，这正是设计想要的节奏感。

### 3.4 为什么不做成「互相卡脖子」

三条防线的规则：

1. 跨树前置只在可选深处（见第一节）。
2. **仙道科技的银两代价是资格线，不是门槛**：灵石才是主门槛。
   反过来说，把城做大能降低仙道的**机会成本**，但不会**锁住**仙道。
3. 每一条正反馈都有天花板：名册容量硬上限、镇守数上限、
   `territoryYieldMult` 是有限项之和、坊市兑换笔数有上限。
   所以「数字稳稳长大」不会变成指数爆炸。

|---|---|---|---|---|
| `surveying` | 营造术 | 900 | realestate | 地产价格 −15% |
| `expansion` | 对外扩张 | 1200 | architecture | 解锁「演武台」 |

| id | 名称 | 成本 | 前置 | 效果 |
|---|---|---|---|---|

### 五 · 致远（T5）—— 以术驭势，家业可久

| id | 名称 | 成本 | 前置 | 效果 |
|---|---|---|---|---|
| `arithmetic` | 算学 | 3500 | finance+household | 银两产出 +10% |
| `vault` | 库房 | 4800 | finance+household | **银两上限 +100%** |
| `courier` | 驿道 | 6000 | trade | 商队耗时 −15% |

> ⚠ `vault` 是本次新加的，而且**非加不可**。它不是「又一项精进」，而是
> 一条被反推出来的必需项：银两上限 = 3000 + 8000×钱庄，而 36 个营造格
> 里钱庄最多占 30 格 → 上限卡在 24.3 万。云深谷坊市的报价是递进的
> （`100000 × 1.20^n`），第 5 笔就要 25 万 —— **超过上限时那一笔永远换不了**，
> 而且玩家看不出任何原因。库房把上限翻倍，报价才追得上。
> 这也是「凡人线反过来被仙道线的需求推着长」的一个真实例子。

### 成本曲线

```
T1    250
T2    320 – 700      ×1.28   （相对 T1 最高）
T3    900 – 1200     ×1.29
T4   1600 – 2600     ×1.33
T5   3500 – 6000     ×1.35   ← 含新增的库房 4800
T6   6500 – 11000    ×1.08   ← 偏平，因为 T6 是「同时开四条支线」
T7  45000 – 60000    ×4.09   ← 大跳，终局节点该有的分量
```

T6 的 ×1.08 是刻意的：这一层四个节点是**并列的四条支线**
（祛障、坊市扩建、义庄、集贤馆），不是阶梯。
T7 的 ×4.09 也是刻意的：终局节点只有真正把城做大的玩家才够得着。

## 五、仙道科技树（完整结构）

成本单位：`灵石 / 银两`。灵石是主门槛，银两是「城里拿得出这笔钱」的资格线。

### 一 · 开脉（T1）—— 破障之后，先要能养得住人

| id | 名称 | 灵石 | 银两 | 前置 | 效果 |
|---|---|---|---|---|---|
| `kaimai` | 开脉 | 12 | 3000 | — | 名册容量 +150 人 · 灵脉矿场出石 +25% |
| `yinling` | 引灵 | 18 | 4500 | — | 天生灵根诞生率 +60% · 城坊产出 +25% |

## 六、仙凡经济（数值口径）

全部在 `src/core/config.js` 的「仙凡经济」一节。改这里就够了，代码里没有魔法数字。

### 城中作坊（凡 → 仙）

```js
CITY_HERB_PER_SEC  = 0.0010   // 每座「药圃」每秒的药材当量
CITY_ORE_PER_SEC   = 0.0008   // 每座「矿寮」的矿料当量
CITY_RUNE_PER_SEC  = 0.0006   // 每座「纸坊」的符料当量
CITY_WORKSHOP_WORKERS = 300   // 每座作坊的用工上限
CITY_LABOR_DEATH   = 0.0000001 // 每名用工每秒的死亡概率
```

```
名义需求 = Σ(座数 × 300)
实际用工(某类) = 人口 ≥ 名义需求 ? 座数×300 : 人口 × (该类需求 / 名义需求)
产出 = 实际用工 × 单产 × (1 + cityMaterialMult)
```

「人是共用的一份」这句话的实体就是 `cityWorkersOf()`：
同一批凡人不会同时在药圃和矿寮做工，所以铺得越多、每座分到的人越少。

### 云深谷坊市（银 → 石）

```js
MARKET_EXCHANGE_BASE_SILVER  = 100000  // 第 0 笔的银两
MARKET_EXCHANGE_BASE_STONES  = 0.5     // 第 0 笔的灵石
MARKET_EXCHANGE_COST_GROWTH  = 1.20    // 第 n 笔比第 n−1 笔贵 1.20 倍
MARKET_EXCHANGE_YIELD_GROWTH = 1.20    // 同时多给 1.20 倍灵石
MARKET_EXCHANGE_MAX          = 12      // 基础可用笔数
MARKET_EXCHANGE_BONUS_PER_TECH = 4     // 每项「撑胃口」的科技 +4 笔
```

```
第 n 笔（n 从 0 起）：
  银两 = round(100000 × 1.20^n)
  灵石 = 0.5 × 1.20^n × (1 + tradeStoneMult)
```

「换过几次」是一条进度线，而不是可以无限刷的按钮。
撑胃口的科技：凡人 `marketexp` / `mutualmarket`，
仙道 `jiexu` / `jielu`（凡研一项 +4 笔）。

**这三个数字是反推出来的，不是拍的**（推导过程写在 `config.js` 的注释里）：

| 约束 | 推出的值 |
|---|---|
| 出 1 名修士的期望成本 = 4 灵石（祛障丹 1 灵石 ÷ 25%） | `BASE_STONES = 0.5`（前三笔约 1.8 灵石，得反复来换，但第一笔立刻能买丹） |
| 银两上限 24.3 万（30 座钱庄）→ 报价必须落在上限内 | `COST_GROWTH ≤ 1.20`（1.35 / 1.26 都会在第 4–6 笔撞上限，实测直接卡死） |
| 上限本身要能长大 | 新增凡人科技「库房」`vaultMult: 1.0`（上限 ×2） |

> 试错记录：`1.35` → 第 4 笔 24.6 万 > 24.3 万上限，卡死；
> `1.26` → 第 6 笔 31.8 万 > 38.8 万上限但银两追不上，也在 5–8 笔处停住；
> `1.20` + 库房 → 实测 8 笔、950 名修士、18 项科技（50 小时）。
> 教训：**报价一旦超过银两上限，这一笔就永远换不了**，
> 而玩家看不出原因 —— 这类死锁必须在数值层排除，不能指望玩家自己绕开。

### 灵脉矿场（仙 + 凡一起）

```
出石/秒 = minWorkers × STONE_MINE_BASE_RATE(0.000045) × grade
          × (1 + 座数 × SPIRIT_MINE_CITY_BONUS_PER(0.25))
          × (1 + mineYieldMult)
矿工死亡/秒 = minWorkers × (0.0000025 + grade × 0.000001) × (1 + mineDeathMult)
```

一条矿脉，两班人：修士以寻龙尺探明矿脉（`c.mineLevel`/`c.mineWorkers`），
凡人搭起采掘队（城里的「灵石矿场」建筑）。两者必须同时存在才出石。

### 灵气池（仙 → 凡）

```js
INNATE_POOL_BONUS_PER = 0.12   // 每座灵池
INNATE_POOL_BONUS_MAX = 1.2    // 上限 +120%
```

灵池花灵石维持（`pool × 0.00013` 灵石/秒），换来的是
**新生婴儿里天生灵根的比例**（`INNATE_CHANCE_PER_BIRTH × (1 + innateBirthMult + innatePoolBonus)`）。
这是闭环那一条：仙道投入 → 好灵根 → 更强的修士 → 更多灵石。

## 八、已知的欠账（下一轮该做的）

诚实列出来，免得下一轮当成新发现：

1. **`trainMult` 还没有接线**。
   `julingzhen`（聚灵符 +15%）与 `yuanying`（+20%）给了这个键，
   但 `cultivation.progressCultivators()` 里还没有乘上它。
   接线点是那一行的 `manualMult*runeMult*metaMult*schoolMult` 里再乘一项。
   加的时候记得把 `cultivationBonuses()` 里的展示也带上。
   （`smoke.mjs` 的「没有未登记的 effect 键」查不出这一条 ——
   它只能证明键被登记了，不能证明它被消费了。所以这一项要人来盯。）

2. **仙道线的「长线目标」还没有兑现为跨周目收益**。
   一局玩不完约 8000 灵石，但目前轮回不带仙道进度。
   `reincarnation.js` 的 `metaOf()` 是现成的挂载点。

3. **`lingzhi`（灵植术）与 `lingtian`（灵田）的效果重叠度高**。
   两者都是 `cityMaterialMult + innateBirthMult`，只是量级不同。
   留着是有意的（长线的「同一件事做得更好」），但如果玩家反馈「点了没感觉」，
   应该把 `lingzhi` 改成给一个**新维度**（例如工坊用工上限）。

4. **仿真的 AI 不会为冲关主动炼丹**（已补上第 0 步，但只有一步）。
   实测补上之后 trade 线从「90 小时停在炼气九层」变成
   「20 小时上筑基初期、点满 23 项仙道科技」，但再往上（金丹/元婴）
   它就停在「炉子等级不够 / 材料不齐」上不动了。
   **要做真正的通关验证，需要把 `aiImmortal` 的材料补货逻辑写完整。**
   这条不是设计欠账，是**测量工具**的欠账 —— 写在这里是因为
   任何人读这份文档里的境界数字，都必须先知道这件事。

5. **仙道侧没有负面效果的节点**。
   凡人侧有 `seeker`（拿命换消息）这种真取舍，仙道侧全是纯增益。
   下一轮可以考虑一个「以寿元换修为」的节点（`immortalCapFlat` 为负、
   `breakBonusFlat` 为正），但**必须先确认它不会与「数字稳稳长大」的支柱冲突**。

6. **城坊的分摊模型在极端配比下会「谁也吃不到」**。
   人口 100、四类作坊各 1 座时，每座只分到 25 人，产量按比例摊薄到 1/12。
   这是刻意的（人是共用的），但界面上目前只显示「满员产量」，
   没有显示**实际用工**。玩家会觉得数字对不上。建议在建筑卡上加一行
   「实际用工 / 需求用工」。

## 九、怎么验

```powershell
cd D:\harness\xiuxian-qi
node scripts/build.mjs                 # src/ → game.html
node scripts/smoke.mjs                 # 633 项断言（含本文件新增的 49 项）node scripts/balance.mjs --baseline    # 静态盘点：孤儿、跨树、effect 覆盖（秒出）
node scripts/balance.mjs               # 三条策略跑满 90 游戏小时
node scripts/balance.mjs greedy        # 单策略
node scripts/balance.mjs --snap greedy # 时间序列快照
node scripts/diagnose.mjs greedy       # 逐项记账：灵石从哪来、到哪去
```

环境变量：

| 变量 | 作用 |
|---|---|
| `XIUXIAN_NO_IMMORTAL=1` | 关掉仙道线的研习（及全部由它解锁的城坊），只留凡人侧同一棵 29 项树。**对照实验就是靠它做的。** |
| `XIUXIAN_TRACE=1` | 把每一次**成功的**操作按时间打出来。查「为什么这一步没发生」时开它。 |

### 每次改动前先定义「失败」

按本项目的口径，「科技线坏掉」的判据是：

- 出现**孤儿节点**（`--baseline` 里合计 > 0）
- 出现**跨树死锁**（主线科技在另一侧为空时被锁死）
- 出现**卡点**（`stalls` 连续 30 分钟无任何可做的事）
- **损银占比 > 100%** 连续超过 5 小时（银两产出大半撞在上限上蒸发）
- 三策略的**最高境界差 ≥ 2 大境界**（说明有一条路线明显走不通）

### 仿真器自身的已知局限（读结论时必须记住）

`balance.mjs` 的 AI 是**够用**而不是**会玩**。它已经修掉的两个坑
（研习被 aiImmortal 抢光、reserve 自锁）写在下文。

仍然存在的局限：**它不会为了冲关去补材料**。实测把「炼丹」接上去之后
（`aiImmortal` 第 0 步），trade 线能从 90 小时停在**炼气九层**
推进到 20 小时就上**筑基初期**并点满 23 项仙道科技 ——
所以后面「仍然停在炼气九层」这个结论**部分来自 AI 不会自己去炼丹，
而不是来自数值**。看境界相关结论时请以这条为准。

### 本次修掉的三个真 bug（都不是「设计」问题，是会毁掉一局的问题）

1. **`mapHoldPower` 顶层重名**。
   `data/map.js` 与 `systems/exploration.js` 各有一份。
   `new Function` 拼装（仿真器与冒烟测试走的路径）能以「后者覆盖前者」跑过去，
   但浏览器里的 ES module 会直接抛
   `Identifier 'mapHoldPower' has already been declared`，
   整段脚本不执行、界面成了空壳（页签、卡片、科技一个都不渲染），
   **而 584 项冒烟测试照样全绿**。
   现在 `smoke.mjs` 有一条文本层面的「顶层声明不得重名」检查。

2. **主线软锁**。第一版让「祛障」require 仙道「引灵」，
   于是「仙道侧不可用」时整条主线永久锁死。
   现在跨树前置只允许落在凡人线的可选深处，
   并有一条回归断言「主线科技『祛障』在仙道侧为空时也可研习（无软锁）」。

3. **仿真器自身的两个自锁**（只影响测量，不影响游戏，但会让人得出错误结论）：
   - `aiImmortal()` 几乎每轮都会返回 true（「把闲人丢去闭关」永远成立），
     而研习被写成 `if (!acted && doTech())` → **研习永远轮不上**，
     三条策略跑满 90 小时一项仙道科技都没点。
   - `doMortal` 里「留够下一笔兑换的银两」的 reserve 上限取了 `silverCap`，
     于是银两顶到上限时条件变成 `silver >= 2×silverCap`，**恒为假**；
     加上商队每 20 秒把银两花到接近零，实测 50 小时 0 笔兑换、0 位修士。
     现在 reserve 上限取 `silverCap × 0.25`，且**换灵石排在商队之前**。
