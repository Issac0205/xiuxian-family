## 一 · 现状诊断（读代码核实，不是读文档）

### 1.1 云深谷坊市**已经存在**，而且只做一件事

`src/data/trade.js` 的 `CULTIVATOR_MARKET` 就是云深谷坊市：

- `requiresSecrets: SECRET_UNLOCK` —— 门是**集齐 10 条秘闻**（`src/core/config.js` 的 `SECRET_UNLOCK = 10`）
- 但它的 `silver: 100000` / `stones: 0.1` 两个字段**只是界面文案用**，真实报价来自 `src/core/formulas.js` 的 `marketExchangeQuote(state, n)`

真实报价（`marketExchangeQuote`）：

```
第 n 笔（n 从 0 起）：
  银两 = ROUND(MARKET_EXCHANGE_BASE_SILVER × MARKET_EXCHANGE_COST_GROWTH^n)
  灵石 = MARKET_EXCHANGE_BASE_STONES × MARKET_EXCHANGE_YIELD_GROWTH^n × (1 + tradeStoneMult)
```

常量在 `src/core/config.js`：`MARKET_EXCHANGE_BASE_SILVER = 100000`、`MARKET_EXCHANGE_BASE_STONES = 0.5`、`MARKET_EXCHANGE_COST_GROWTH = 1.20`、`MARKET_EXCHANGE_YIELD_GROWTH = 1.20`、`MARKET_EXCHANGE_MAX = 12`、`MARKET_EXCHANGE_BONUS_PER_TECH = 4`。

**⇒ 由此得到一个本文全篇都要用的关键事实**：两侧同以 `1.20^n` 增长，所以

```
买入单位价  P = 银两 / 灵石 = 100000 / 0.5 / (1 + tradeStoneMult) = 200000 / (1 + tradeStoneMult)   银两/灵石
```

**P 与 n 无关**。`config.js` 的注释把它说成设计意图（「两者同速，所以兑率本身不变，变的是这一笔的规模」）——本文把它**升级成一条不变式**，反套利证明全靠它（§五）。

现存能力清单（这就是「通商太单薄」的全部内容）：

| 能力 | 现状 | 代码位置（符号） |
|---|---|---|
| 银两 → 灵石 | ✅ 有，递进、限量 | `planExchange` / `commitExchange`（`src/core/engine.js`）、`marketExchangeQuote` / `marketExchangeLimit`（`src/core/formulas.js`） |
| 灵石 → 银两 | ❌ **没有** | — |
| 灵石 → 祛障丹 | ⚠️ 有，但**不在坊市里**，而且门是**科技**不是秘闻 | `planPill` / `commitPill`（`src/core/engine.js`）+ `src/data/pills.js` |
| 地区开放权 | ❌ **没有**（只认 10 条秘闻，与地图无关） | — |
| 商品购买权 | ❌ **没有** | — |
| 其它商品 | ❌ 没有 | — |

### 1.2 两处既有缺陷（本轮顺手发现，与用户设想无关但会挡路）

**缺陷 ①：`CULTIVATOR_MARKET` 的报价字段与真实公式不同步 —— 界面显示错了 5 倍。**

- `src/ui/app.js` 的 `updateMarket` 读的是 `CULTIVATOR_MARKET.silver` / `CULTIVATOR_MARKET.stones`（`100000` / `0.1`）
- 而真实执行者 `planExchange` → `marketExchangeQuote` 给的是 `100000` / **`0.5 × (1 + tradeStoneMult)`**
- ⇒ 首笔兑换**界面写「→ 0.1 灵石」，实际到手 0.5 灵石**（差 5 倍）。且 `done ≥ 1` 之后界面按 `100000` 判「买得起」，真实要 `100000 × 1.2^n`，按钮会在银两不足时仍然是可点状态（点了才失败）。

**⇒ 修法（本文 §十 落地项 1）**：`CULTIVATOR_MARKET` 只保留**叙事元数据**（`id` / `name` / `icon` / `desc` / `requiresSecrets`），**删掉 `silver` / `stones` 两个字段**，让 `updateMarket` 改读 `marketExchangeQuote(state, marketExchangeCount(state))`。**一个数只能有一个真相源**——这正好是本块要新增商品表时必须先立好的规矩，否则新坊市会把这个坑复制 N 份。

**缺陷 ②：`immortal-techs.js` 里已经在用「线索口径」，但两处旧数字仍在文档里流传。**

`src/data/immortal-techs.js` 的 `jiexu`（界墟）节点注释明确写：

> 旧表把「参悟」按 10 本算 ⇒ 需求 59、余量 +56%；实测是 24 本 × 2 = 48，旧口径的 +56% **已被设计师撤回**（§十二.4 明令禁止再复述该数字）。
> 现口径：硬需求 28、硬需求+洞天 39、一遍全参悟 87、满级 240。

⇒ 本文**只使用现口径**（28 / 39 / 87 / 240），并把它当作 §九 的分母。**如果哪份文档还在写「+56%」，那是被撤回的旧数字。**

## 二 · 三层数据结构

```
第一层  地区（地区 = 地图上的一个 foe 节点）
        └─ 占领它 ⇒ 该地区「坊市开放权」（marketOpen）
第二层  坊市（一座坊市挂在正好一个 foe 节点上）
        └─ 逐件花「线索」买断 ⇒「商品购买权」（marketGoodUnlocked）
第三层  商品（四类 kind）
        └─ exchange 银两↔灵石 / pill 丹药 / material 材料 / clue 线索
```

**设计约束（先立规矩）**：

1. **一座坊市 = 一个 `foe` 节点**。`src/data/map.js` 的 `MAP_NODES` 里 `kind === 'foe'` 的**恰好 4 个**：`valley`（青木寨）、`river`（黑水门）、`ridge`（玄铁宗）、`beastnest`（万兽谷）⇒ **天然上限 4 座坊市**，不需要新增地图格，也不需要改 `MAP_COLS` / `MAP_ROWS` / `mapNeighbors`。
2. **汇率只有一处**：所有坊市的银两↔灵石**共用** `marketExchangeQuote` 的 P（§五）。后续坊市**只许改「卖什么」，不许改汇率** —— 一旦各坊市自带汇率，跨坊市低买高卖立刻成立。
3. **商品表与坊市表分离**：商品是「什么东西」，坊市是「谁在卖」。同一件商品可以在多座坊市出现（如材料），但**独占商品只在一处**（§七）。

### 3.1 规则

```
marketOpen(state, siteId)  ⇔  mapHeld(state, site.nodeId)          ← 占领
```

## 四 · 第二层：秘闻 → 商品购买权（**货币由主策裁定为「秘闻」**）

> ⚠ **本节经历过一次推翻，留档**：本文初稿（依据当时代码）论证「`state.secrets` 不能花，所以商品权只能挂在 `clues` 上」。
> **主策随后裁决「秘闻必须是消耗品」** ⇒ 该结论作废，改以秘闻作货币；`clues` 的预算**完全让出来**（§九）。

> ⚠ 他给的引证里带 `文件:行号`，本文按 `docs-code-reference-drift.md` R7 **一律改写成符号名**（行号半衰期以小时计）。

### 4.1 命名钉子（**必改项**）：一个词不能指两个资源

| | **秘闻** `state.secrets` | **线索** `cultivation.clues` |
|---|---|---|
| 类型 | **下标集合**（每条唯一，元素是 `src/data/trade.js` 的 `SECRETS` 里的一句原文） | **整数** |
| 上限 | **20**（`SECRETS.length`，池子硬顶，只增不减） | 无上限（可再生） |
| 产出 | 商路寻秘 `MORTAL_ROUTE.secretChance`（0.01/趟）+ 科技 `secretChance` + `explorePerSec`（`advanceCultivation`） | ① 每条新秘闻 +1（`grantSecret`）② `cluePerSecFlat` 慢路 2.16 条/时 ③ 投帖 `ERRAND_CLUE_PER_SEC` |
| 消耗 | 现状**无**；改造后 = **解锁坊市商品购买权** | 冲关 `REALM_GATES[*].clues`（**成功后**扣）、洞天入场 `MAP_NODES[*].clues`、参悟 `MANUAL_ATTUNE_CLUE_COST` |
| 门槛用途 | 坊市开放 `CULTIVATOR_MARKET.requiresSecrets`、凡人科技 `requiresSecrets`、`pool-blueprint` 12、`compass` 15 | 无（它本身就是被消耗的那个数） |
| UI | 「当前 N/10 条秘闻」 | 「可用线索 N 条」 |

**⚠ 现存同词两义（实测原句）**
- `planExchange` 的拒绝理由：「须先集齐 10 条**秘闻**」→ 读 `secrets`
- `breakthroughPlan` 的拒绝理由：「冲关需 N 条**秘闻线索**」→ 读 `clues`

⇒ **同一个词在两条链上指两个不同资源**，玩家与实现者都会混。
⇒ **钉死**：`secrets` = **秘闻**；`clues` = **线索**；所有把 `clues` 叫成「秘闻线索」的文案统一改写（文案属 `src/**`，另派实现任务）。

⇒ ⚠ **顺手记一处「同一规则写在两处」**：`pool-blueprint` / `compass` 的 **12 / 15** 两个门槛，在 `src/systems/immortal-actions.js`（**硬编码字面量**）与 `src/main.js`（按钮 `disabled` 条件）里**各写了一份**。本块要动的正是这两个数所在的判定口径，**改一处必须改两处**（或先抽成一个符号）。

### 4.2 数据模型：**累计 + 已花费**双集合

**一、模型**
```
state.secrets      保持不变（累计已发现，下标集合，只增不减；它同时是「门槛」口径）
state.secretsUsed  新增（已花费的下标集合）
secretsAvailable = state.secrets.length − state.secretsUsed.length      ← 可花费量
```

- **抽池判重仍只用 `secrets`** —— `grantSecret` 里的 `pool.filter(i => !state.secrets.includes(i))` **不改**
  ⇒ **同一条秘闻永不重复出现**（保住 `src/data/trade.js` 的「抽到过的不会重复抽」约束）；**代价：池子一去不回，20 条是硬顶**
- **门槛一律读累计 `secrets.length`，不读可用量** ⇒ 花费**不会关掉已开的门**
- **不改成整数计数**：会丢掉「抽到过的不会重复抽」，也更难审计
- **`secretsUsed` 必须是下标集合**（不是计数）—— 与 `secrets` 同构，才能做「同一件商品不能买两次」「已花的是哪几条」这类断言

**二、⇒ 由此得到一条必须写死的结论：`保留门槛` 不占预算。**
门槛读**累计**，而累计只增不减 ⇒ 花到 0 可用量既不会关门、也不会阻止未来把累计推到 15。
（这条纠正了初版「预算 = 20 − 15 = 5」的过紧算法 —— 按那个算法只能放 1~2 件商品。）

### 4.3 解锁规则与价目

```
marketGoodUnlocked(state, siteId, goodId)  ⇔  state.cultivation.marketGoods[siteId] 含 goodId
unlockMarketGood(state, siteId, goodId)：
   前置 ① marketOpen(state, siteId)（§三 —— **开放权只能由征伐给**）
   前置 ② secretsAvailable ≥ good.price
   成功 ③ secretsUsed.push(该秘闻的下标)；marketGoods[siteId].push(goodId)
```

**方案 A（主策定案）：坊市开放那 10 条只是门槛，不花。**
依据是用户原话的结构 —— 「通过**征伐**获得一个地区的坊市**开放权**，然后通过**秘闻**解锁坊市里面的**商品购买权**」⇒ 开放权归征伐，秘闻只花在商品这一层。`CULTIVATOR_MARKET.requiresSecrets`（=10）保持门槛语义，**不消耗**；既有六处 `.length` 门槛（`planTech` / `planExchange` / `pool-blueprint` / `compass` / `app.js` 两处）**全部不动**。

**价目（Σ 刻意 > 池子，见 §4.4）**

| 坊市 | 商品 | 价（秘闻） |
|---|---|---|
| 云深谷（`valley`） | 银两 → 灵石 | **0**（已有 10 条门槛，不重复收费） |
| | 灵石 → 银两 | 3 |
| | 祛障丹批发权 | 3 |
| 黑水渡（`river`） | 银两 → 线索 | 4 |
| | 寒潭菱（本地材料）双向 | 3 |
| 玄铁宗（`ridge`） | 玄铁芝 / 玄铁 双向 | 4 |
| | 法器整修 | 5 |
| 万兽谷（`beastnest`） | 成药（溢价买入） | 6 |
| **合计** | | **28** |

单件最大 6 ≤ 20 ✓。20 条预算下按价排序累计 `3,3,3,4,4,5,6` ⇒ 买满 **5 件**要 17 条，第 6 件会到 22 > 20 ⇒ **一周目最多买 5 件，必须放弃 ≥ 2 件**。

### 4.4 预算分配：Σ = 28 > 池子 20 —— **这是设计，不是 bug，但有前置条件**

**主策裁决 (甲)**：允许 `Σ商品 > 池子`，把「总量守恒」换成 **5 条替身断言**。
理由（拆法比初稿更干净）：`SECRETS.length ≥ Σ` 的**原始用途**是防「四道门槛 28 > 池子 20」那种**主线走不通**；而 **Σ > 20 是设计意图**（排他取舍）⇒ **同一条断言不能同时管住这两件相反的事**。按「**谁受总量约束**」拆开：

| 对象 | 约束 | 为什么 |
|---|---|---|
| **门槛**（`planTech` / `planExchange` / `pool-blueprint` / `compass`） | **必须 `需求 ≤ SECRETS.length`** | 它们是 `.length` 比较、**不消耗** ⇒ 超池子 = **主线永久走不通** |
| **商品**（坊市购买权） | **只约束单品** `price_i ≤ SECRETS.length` | Σ > 池子是**设计意图**（取舍） |

**五条断言（本节的契约，落成 `smoke.mjs` 断言）**

| # | 断言 | 防的是什么 |
|---|---|---|
| 1 | **单品可负担**：`∀i: price_i ≤ SECRETS.length` | 「永远买不起」的**死内容** |
| 2 | **预算可见**：界面渲染「总量 / 已花费 / 余量」三数，且 `总量 − 已花费 === 余量` | 取舍**看不见** ⇒ 从设计变劝退 |
| 3 | **不可透支**：任何时刻 `secretsUsed.length ≤ secrets.length`；余量不足 ⇒ `{ok:false}` 且**点名理由**（话术口） | 透支 / 静默失败 |
| 4 | **门槛不受消耗影响**：花费前后 `secrets.length`（累计）**不变**、`secretsUsed.length` **恰 +1** | 花费**自毁已开的门**（科技锁回去 / 坊市关闭） |
| 5 | **门槛需求 ≤ 池子总量**：`∀门槛 g: g.requiresSecrets ≤ SECRETS.length` | 门槛本身超池子 ⇒ **主线永久走不通** |

> **主策原话**：这是「**取舍**」与「**死内容**」的分界线 —— 前者是设计，后者是 bug。

**⇒ 初稿那条朴素守恒断言（`SECRETS.length ≥ Σ消耗`）作废**（与 Σ = 28 直接冲突，写出来永远红）。它管的对象已由断言 5 接手。

### 4.5 「时间闸门」：**货币早到、花费分散、信息全公开**

实跑证据（`docs/91 §2.3` 的 greedy 实跑）：**秘闻在第 2 小时就集齐 20/20**，此后池空。
初稿把它读成「闸门失效」，**这个判断是看窄了**。正确处理是三条：

1. **闸门由别的东西接管，而且已经在了**：坊市本体要 `CULTIVATOR_MARKET.silver = 100000` 银两；开放权要**打下对应 `foe` 节点**（`valley` 110 / `river` 560 / `ridge` 2400 / `beastnest` 12000 战力）⇒ **玩家第 2 小时拿到「钥匙」，第 20 小时才见得到「门」**。
2. **花费被自然分散（典型情况下是 4 个时点）**：`unlockMarketGood` 的前置 ① 是 `marketOpen` ⇒ **秘闻只能在已开放的坊市里花**。
   **典型路径下确实分四次 —— 但这是解析推导，不是猜测**：
   - 四个 `foe` 节点的 `power` = **110 / 560 / 2400 / 12000** ⇒ 相邻比 **5.1× / 4.3× / 5.0×**
   - 而境界战力阶跃大得多（`cultivateBasePower`：炼气 10→549、筑基 1200→6998、金丹 20000、元婴 500000）⇒ **每个节点大致要求「比上一个多一个境界」**
   - 按 `docs/00` 的节奏（炼气 3.56h / 筑基 +4h / 金丹 +7h / 元婴 +12h）⇒ **相邻坊市的达成时点大致相隔一个境界，即数小时**
   ⇒ **这一条解决了「决策发生在信息最少的时候」**：你能看到第一座坊市的价目之后，再决定后面怎么分。
   ⚠ **但它不被强制 —— 反例见 §4.5.1。**
3. **价目全程公开**（本文新增）：**未开放的坊市也显示它卖什么、多少钱**（当作「听闻」/图鉴），只是不能买。
   ⇒ 主策那句「**看得见的取舍叫设计，看不见的取舍叫劝退**」全靠这一条落地。
   ⇒ 界面必须给：每件商品的**效果一句话** + **价格** + **当前总量/已花费/余量**。

### 4.5.1 ⚠ 反例：「分四次」不被强制（本节实测）

（这一节是**游戏设计师要求「补验证、否则不许当结论写」**之后补上的。他的要求是对的 —— 原稿那句「分四次」当时确实是**未经核实的结论**。）

```
mosscave（起点）→ mistcave → grotto → wastes      全程只花 17.2 灵石 + 11 条线索
```

**因此本节的标准表述是**：

> **典型路径：分四次（相邻坊市相隔约一个境界）；但这是战力曲线带来的常态，不是被规则强制的性质。**

**若要强制，两条硬化方案（都要新增判定，代价列出）**

| 方案 | 做法 | 代价 |
|---|---|---|
| H1 | `marketOpen` 再加一条**境界门**（如「族中至少一名 ≥ 该地 `realm` 的修士」） | 新增门槛口径；且 `MAP_NODES[].realm` 现在只用于洞天建议境界，语义要借过来 |

**本文选「不做」**：它的成本只是「某几座挤在一起」（玩家仍然只能在 20 条里选，**取舍本身没有消失**）；而 H1/H2 的成本是新增门槛与状态抖动。

## 五 · 第三层：统一定价律与反套利论证

> 这一节是整个设计的地基。**如果这一节不成立，这个设计就不该做。**

### 5.1 统一定价律

引入**唯一汇率真相源**（新增到 `src/core/formulas.js`）：

```js
/** 1 枚灵石值多少银两。全游戏唯一汇率。 */
function silverPerStone(state) {
  const fx = techEffects(state);
  return MARKET_EXCHANGE_BASE_SILVER / MARKET_EXCHANGE_BASE_STONES / (1 + fx.tradeStoneMult);
}
```

代入常量：`silverPerStone = 100000 / 0.5 / (1 + tradeStoneMult) = 200000 / (1 + tradeStoneMult)`。
- `tradeStoneMult = 0`（开局）⇒ **200000 银两/灵石**
- `tradeStoneMult = 0.25 + 0.35 + 0.6 + 0.4 = 1.6`（`marketexp` + `mutualmarket` + `jiexu` + `jielu` 全研）⇒ **76,923 银两/灵石**

⚠ **这**不是本文发明的新数 —— 它就是 `marketExchangeQuote` 里 P 的解析式，本文只是把它**提取成一个符号**，让买卖两侧引用同一个函数。`marketExchangeQuote` 改写成引用它（等价变形，数值一字不变）。

**四类商品的买卖价**：

| kind | 买（付出去） | 卖（收回来） |
|---|---|---|
| `exchange` 银两 → 灵石 | 付 `marketExchangeQuote(state, n).silver` 银两，得 `.stones` 灵石（**既有，一字不改**） | — |
| `exchange` 灵石 → 银两 | — | 给 `T` 灵石，得 `T × silverPerStone(state) × (1 − MARKET_SPREAD)` 银两 |
| `pill` 丹药 | 付 `PILL_STONE_COST × count × (1 − MARKET_PILL_DISCOUNT)` 灵石 | **不可卖**（丹药不能换回灵石） |
| `material` 材料 | 付 `count × matBasePrice(Mat) / (1 − MARKET_SPREAD)` 灵石 | 得 `count × matBasePrice(Mat) × (1 − MARKET_SPREAD)` 灵石 |
| `clue` 线索 | 付 `count × MARKET_CLUE_PRICE_STONES × silverPerStone(state)` 银两 | **不可卖**（线索只有买入方向，见 5.3） |

新增常量（`src/data/markets.js`）：

```js
const MARKET_SPREAD = 0.20;              // 坊市抽成：卖出相对买入的同币种折损
const MARKET_PILL_DISCOUNT = 0.10;       // 坊市熟客九折（上限，防骨折）
const MARKET_CLUE_PRICE_STONES = 0.5;    // 1 条线索 = 0.5 灵石（待校准）
const MARKET_SELL_MAX = 6;               // 卖出笔数上限基数
const MARKET_SELL_BONUS_PER_TECH = 2;    // 每项 tradeStoneMult 科技 +2 笔
const MATERIAL_STONE_PRICE = { grass: 0.05, ling: 0.07, iron: 0.10, flame: 0.12 };  // 待校准
```

### 5.2 反套利论证（三部分，缺一不可）

设 `p = silverPerStone(state)`（银两/灵石），`φ = MARKET_SPREAD = 0.20`。

**① 同币种回路严格为负（单坊市内）**

- 买入侧：付 `S` 银两 → 得 `S / p` 灵石（单位价 `p` 银两/灵石）
- 卖出侧：给 `T` 灵石 → 得 `T × p × (1 − φ)` 银两（单位价 `p(1 − φ)` 银两/灵石）
- ⇒ **卖价 / 买价 = (1 − φ) = 0.80 < 1**，**与 n 无关、与 `tradeStoneMult` 无关**（两侧同乘 `p`）

于是任一含卖出的回路：

```
银 → 石 → 银：  S 银 → S/p 石 → (S/p)·p·(1−φ) = S(1−φ) 银   ⇒ 净 −φS = −20%
石 → 银 → 石：  T 石 → T·p(1−φ) 银 → T(1−φ) 石             ⇒ 净 −φT = −20%
```

**方向对称，折损都是 20%。** 纯买入序列（只做银→石）不产生银两，所以不存在「只买入就能赚」的路径。∎

**② 科技不变式：研究科技不改变比值**

`p` 里含 `(1 + tradeStoneMult)`，**买卖两侧引用同一个 `p`** ⇒ 比值恒为 `0.8`，与科技无关。

⚠ **这是最容易犯的错，写成显式反例**：如果卖出价**不**乘 `(1 + tradeStoneMult)`（即卖出按固定 200000 而买入按 `200000/(1+m)`），那么

```
买入 1 灵石实际花 200000/(1+m) 银两，卖出 1 灵石得 200000 银两 ⇒ 净赚 200000·m/(1+m) 银两
全科技 m = 1.6 时 ⇒ 每灵石净赚 123,077 银两 —— 这就是无限套利。
```

⇒ **卖出价必须与买入价共用同一个 `p`。** 这一条要写进 `smoke.mjs` 的断言（§十二）。

**③ 跨坊市不变式：不许自带汇率**

所有坊市的银两↔灵石都走 `silverPerStone(state)`。若某座坊市自带一套汇率（哪怕只差 1%），则

```
在便宜的坊市买入、在贵的坊市卖出 ⇒ 净赚差价，且可无限重复
```

⇒ **后续坊市只许改「卖什么」，不许改「怎么算钱」**（§二 设计约束 2）。

**④ 上限不是反套利的依据，是经济闸门**

读代码时会发现 `MARKET_EXCHANGE_MAX = 12` 也限制了总量。**但反套利不依赖它** —— 上面前三条与笔数无关。上限的作用是**防止灵石→银两变成无限印钞机**（否则玩家可以拿领地赋税出的灵石，把银两上限直接买满，绕过全部银两经济）。

⇒ 卖出侧用**独立**的笔数上限 `MARKET_SELL_MAX`（+ 每项科技 `MARKET_SELL_BONUS_PER_TECH`），**不吃** `exchangeCount`。
**为什么独立**：若共用 `exchangeCount`，玩家把 12 笔买满后就**永远**不能卖灵石了（晚期玩家最需要银两时反而不能用）；而独立性不会打开套利口子，因为套利由 20% 折损独立堵死。

**⑤ 还有一层天然保护：银两有上限，超出的会蒸发**

`src/core/engine.js` 的 `simulate` 里银两受 `derive(state).silverCap` 夹取（`silverCap = ROUND((BASE.silverCap + 银行数 × BANK_CAPACITY) × (1 + vaultMult))`，`BASE.silverCap = 3000`、`BANK_CAPACITY = 8000`）。
⇒ 玩家在银两**已经贴顶**时卖灵石是纯亏（进账直接蒸发）。所以「灵石→银两」的真实用途被限制在**刚花掉一大笔银两之后**（例如付科技 `cost`）——这恰好是它该有的用途。

### 5.3 为什么「线索」只允许买入、不允许卖出

线索**没有卖出方向** ⇒ 「银两→线索→银两」这条回路在结构上不存在，不需要折损论证。
（如果哪天要给线索开卖出方向，**必须**用同一个 φ 重做 §5.2 的三条证明 —— 现在没有这个必要。）

同理，丹药（`pill`）只买不卖：否则「灵石→丹→灵石」会与 §5.2 的汇率打架，或与炼丹的材料成本形成套利。

### 5.4 ⚠ 真正需要盯的环不是「银两→灵石→银两」，而是「银两→灵石→灵池→修士→银两」

**全 `src/` 扫描的结论（游戏设计师 t2 出，本文复核）**：**现存代码里不存在任何 `spiritStones → silver` 转换** ——
灵石只出现在**成本侧**（`planExchange` / `commitPill` / `planImmortalTech` / `planManualAttune` / `breakthroughPlan` / `forgeRate` / `runePending` / `schools` / `roots` / `immortalAction` 各处）；
`sellRefund`（`SELL_RATIO = 0.5`）是**建筑→银两**，与灵石无关。

⇒ **所以「银两→灵石→银两」这条环今天是闭合不上的** —— 它不是被定价堵住的，是**结构上没有反向边**。
**而本节 §5.1 正是在开这条反向边**（灵石→银两）。所以：

> **§5.2 那三部分证明不是「确认既有安全」，而是「为本文新增的反向边补安全证明」。**
> 换句话说：**这条环的风险是本文引入的，也必须由本文堵死。**

**真正存在的环是另一条，而且它不是本文引入的**：

```
银两 → 灵石（marketExchangeQuote）
     → 灵池（advanceImmortalEconomy：成本 c.pool × 0.00013 灵石/秒）
     → 觉醒修士（addCultivator）
     → laborMult = min(2, workUnits × 0.08)  →  derive().silverPerSec ↑
```

它的正确表述是「**不可无限放大**」，**不是**「每步都亏」：

- `laborMult` **硬封顶 2** ⇒ 收益增量上界 `人口 × 0.12 × 2` 银两/秒；且 `workUnits ≥ 25` 之后**边际收益为 0**
- 灵池成本**随池数线性增长**（`c.pool` 直接进成本式），修士数另受 `cultivatorLimit(state)` 卡着
- ⇒ **边际收益归零而边际成本继续涨 ⇒ 存在有限最优点，越过后必亏**

**量级（t = 0，`tradeStoneMult = 0`）**
```
1 灵石 = 200000 银两                        （§5.1）
1 座灵池 = 1 × 0.00013 灵石/秒 = 26 银两/秒
覆盖它需 人口 × 0.12 × laborMult ≥ 26  ⇒  laborMult = 2 时 人口 ≥ 108
```
⇒ 小规模时它**确实净赚**（这是设计意图：仙养凡 → 凡养仙），但**靠加池无限放大不成立**。

**⇒ 由这条推出本块的一条设计纪律**：
**不得**让坊市给 `laborMult` / `silverPerSec` / `pool` 任何形式的加成。
本块商品只有四类 —— `exchange` / `pill` / `material` / `clue` —— **没有一类触碰这条环的任一环节**（唯一擦边的是 `clue`：线索加快冲关，但冲关不改变 `silverPerSec`）。

```
……
n = 11: 100000 × 1.20^11 = 743,008 银两 → 0.5 × 1.20^11 = 3.716 灵石
全 12 笔合计：银两 100000 × (1.20^12 − 1)/0.20 = 3,958,000；灵石 0.5 × (1.20^12 − 1)/0.20 = 19.79（× (1+m)）
```

⚠ 注意最后一行：**全 12 笔合计要 396 万银两**，而银两上限约 `3000 + 8000 × 银行数`（`vaultMult` 可翻）。这正是 `config.js` 那段注释在讲的事（「第 n 笔的报价必须落在银两上限之内，否则这一笔永远换不了」）。⇒ **坊市是「随时间攒出来」的，不是「一次买完」的**；这也解释了为什么本文**不新增**灵石→银两以外的新银两产出口（§八）。

### 6.2 第 3 笔为什么要拆成「批发权」而不是「整条搬进坊市」

`src/data/pills.js` 的注释定义：祛障丹是**凡人篇的最后一道门**，而且「**目前只有祛障丹是坊市可买的丹**，其余丹药都在 `src/data/alchemy.js` 的丹方表里，要自己采药、起炉、炼出来」。

- 现行门槛是**科技** `quzhang`（`pill.requiresTech`），不是秘闻。**这个科技门不能删** —— 它是凡人科技线的一个进度节拍（`src/data/techs.js` 的 `quzhang`）。
- 所以坊市商品「丹房」买的是**权**：解锁后 `planPill` 支持**一次买多枚**（`count`，上限 10），并享 **九折**。
- **为什么不给更低折扣**：`src/data/alchemy.js` 里祛障丹的丹方原文就是 `materials: { grass: 2 }`、`baseRate: 0.90`、`yield: 1`，而它的 `desc` 已经写死了设计意图：「**坊市亦有售，但自炼便宜得多。**」

  解析验算（守这条意图）：自炼 1 枚的期望材料 = `2 / 0.90 = 2.22` 株青灵草；按 §5.1 的材料基准价 `MATERIAL_STONE_PRICE.grass = 0.05` ⇒ **0.111 灵石**。坊市九折后 = `1 × 0.9 = 0.9` 灵石 ⇒ **坊市仍是自炼的 8.1 倍**。「自炼便宜得多」**成立**。
- **额外好处**：批量买丹是**玩家主动操作**，不进离线路径 ⇒ 与 T-10「离线只推凡人」的口径天然一致（离线不产人，在线想快就花钱）。且仍受 `cultivatorLimit(state)` 与 `state.population ≥ 1` 门控（`planPill` 已有）。

## 七 · 后续三座坊市（各自独占一样东西，不换皮）

**共同骨架**（每座都一样，这是「成一块」的意思）：本地材料买卖（`material`）+ **一件仅此一家的主题商品**。
**区分点**：挂在不同 `foe` 节点 ⇒ 不同 `power` ⇒ 不同**境界**；不同材料 ⇒ 不同**下游产线**；不同主题商品 ⇒ 不同**玩法动机**。

### 7.1 黑水渡坊市 ← `river` 黑水门（`power: 560`，筑基期）

**独占：线索本身。** 全游戏**唯一**能把银两变成线索的地方。

- 卖：`银两 → 线索`，价 `MARKET_CLUE_PRICE_STONES (0.5 灵石) × silverPerStone(state)` ⇒ 开局 **100000 银两/条**（`0.5 × 200000`），全科技 **38,462 银两/条**（`0.5 × 76923`）
- 买：**不卖**（线索只有买入方向，§5.3）
- 本地材料：`ling` 寒潭菱（`src/data/alchemy.js` 的 `ALCHEMY_MATERIALS` 里 `node: 'river'`）

**为什么值一座坊市**：它是 §九 那个「余量只有 29.3 条」的**解药** —— 让线索从**硬上限**变成**软上限**（缺了就花银两买）。而银两在终局是**贴顶溢出**的（§5.2 ⑤），所以这条正好给「溢出的银两」找到了出口。

**与科技线的关系**：`jiexu`（界墟）给 `cluePerSecFlat: 0.0004`（即 +1.44 条/时）与 `tradeStoneMult: 0.6` —— **同一位科技同时让你「自然涨线索」和「更便宜地买线索」**，两件事一口径，不需要新科技。
**与境界的关系**：`river` 是 `MAP_NODES` 里第二个 foe（tier 2）⇒ 自然落在筑基期。

### 7.2 玄铁宗坊市 ← `ridge` 玄铁宗（`power: 2400`，金丹期）

**独占：本地产的矿料与药材的「双向」交易**，即**唯一能把过剩材料变现**的地方。

- 卖（`material`）：`灵石 → xuantie 玄铁` / `→ iron 玄铁芝`（买入价 = `基准价 / 0.8`）
- 收（`material`）：`矿料/药材 → 灵石`（价 = `基准价 × 0.8`）
- 材料表出处：`src/data/map.js` 每个节点的 `herb` / `ore` / `rune` 字段 + `src/data/alchemy.js` 的 `ALCHEMY_MATERIALS`（含 `node` 字段，**已把每种药材绑到它的产地节点**）+ `src/data/forge.js` 的 `FORGE_ORES` + `src/data/runes.js` 的 `RUNE_MATERIALS`

**为什么值一座坊市**：领地与 `advanceCityWorkshops` 会**持续**产出材料（`map.js` 里 `herbYield` / `oreYield` / `runeYield`，城市侧由 `CITY_HERB_PER_SEC` 等驱动），而材料的**唯一出口**是炼丹/炼器/炼符的配方消耗。缺一味药时前面全白搭、多出来时全浪费 —— 这一买一卖**同时修两头**。

**经济权重被刻意做小（这是它的安全阀）**，解析验算：
- 全部 4 药草合计 `herbYield = 0.002 + 0.0015 + 0.001 + 0.0008 = 0.0053 /秒` ≈ **19.1 株/时**
- 按 `MATERIAL_STONE_PRICE` 加权（`grass 0.05 / ling 0.07 / iron 0.10 / flame 0.12`）≈ `0.0053 × 0.08 ≈ 0.00042 灵石/秒` ≈ **1.5 灵石/时**
- 对比：全部领地赋税 `yield` 合计 `0.001 + 0.003 + 0.010 + 0.025 = 0.039 灵石/秒` ≈ **140 灵石/时**（还要乘 `territoryYieldMult`、`moralityTaxMult`）
⇒ **材料变现的收益只有赋税的约 1%** ⇒ **不可能靠卖材料绕过灵石经济**。它的价值在「补缺口」与「不浪费」，不在产出。

**与科技线的关系**：`lingzhi`（灵植术，`cityMaterialMult: 0.80`）与城市建筑决定材料**产量**；产量越高，坊市的**补缺能力**越值钱 —— 科技抬的是需求侧，不是汇率。
**与境界的关系**：`ridge` tier 3 ⇒ 金丹期。

### 7.3 万兽谷坊市 ← `beastnest`（`power: 12000`，元婴/化神期）

**独占：成药。** 全游戏**唯一**能买「本该自己炼的丹」的地方。

- 卖（`pill`）：`灵石 → ALCHEMY_RECIPES 里的丹`（`筑基丹` / `金丹` / `元婴丹` / `化神丹` / `凝丹丸` / `九转丹`）
- **不解锁丹方**（`ALCHEMY_RECIPES` 本身不动），所以「炼丹」仍然是**唯一**能自主供丹的路
- 定价律（把炼丹成本当参考价，再乘一个**惩罚溢价**）：

```
marketPillPrice(craft） = (Σ 材料数量 × MATERIAL_STONE_PRICE) / baseRate × MARKET_PILL_PREMIUM
MARKET_PILL_PREMIUM = 1.6      // 待校准
```

  解析示例（`筑基丹`，`materials: { grass: 3, ling: 1 }`、`baseRate: 0.55`）：

```
自炼材料成本 = 3 × 0.05 + 1 × 0.07 = 0.22 灵石
坊市售价     = 0.22 / 0.55 × 1.6 = 0.64 灵石        ⇒ 坊市是自炼的 2.9 倍
```

  ⇒ **自炼永远更便宜**（差 ~3 倍），坊市买的是**时间**（不必起炉、不必等 `months`）。
- 本地材料：`flame` 赤焰花（`ALCHEMY_MATERIALS` 里 `node: 'beastnest'`）

**与科技线的关系**：`jiuzhuan`（九转丹房）的 `unlocksPill: 'jiuzhuandan'` 是**丹方**解锁 —— 坊市卖的是**同一批丹的成品**，所以科技线掌握「能不能自炼」，坊市掌握「能不能买现成」。两条不冲突，且**科技线优先**（自炼便宜 3 倍）。
**与境界的关系**：`beastnest` tier 4、`power: 12000` ⇒ 元婴/化神期。这条**正好服务本轮「每个境界都有自己独特玩法」的目标**：元婴/化神玩家多出一条「花钱跳过炼丹排队」的操作。

### 7.4 四座坊市的对照

| 坊市 | 节点 | power | 对应境界 | 独占商品 | 动机 |
|---|---|---|---|---|---|
| 云深谷 | `valley` 青木寨 | 110 | 炼气 | **银↔石双向** + 祛障丹批发 | 「我要灵石 / 我要人」 |
| 黑水渡 | `river` 黑水门 | 560 | 筑基 | **线索**（银两买） | 「我要冲关，线索不够」 |
| 玄铁宗 | `ridge` 玄铁宗 | 2400 | 金丹 | **材料双向** | 「我差一味药 / 我多了一堆料」 |
| 万兽谷 | `beastnest` 万兽谷 | 12000 | 元婴·化神 | **成药** | 「我不想等炼丹」 |

⇒ 四座的动机**互不重叠**，且都挂在**既有节点**上，没有新增一格地图。

## 八 · 与现有经济的关系（硬问题 2）

### 8.1 `CULTIVATOR_MARKET` / `marketExchangeQuote`：**保留，且数值一字不改**

坊市只做两件事：**在它外面加两把钥匙**（地区权、商品权），**在它旁边加一个反向口**（灵石→银两）。
`marketExchangeQuote` 的公式、`marketExchangeLimit` 的规则、`MARKET_EXCHANGE_*` 六个常量**全部不动**。
（唯一改动是缺陷 ① 的修法：把 `CULTIVATOR_MARKET.silver/stones` 删掉，让界面改读同一个函数 —— 这是**让界面变对**，不是改数值。）

### 8.2 炼丹（`src/data/alchemy.js` + `src/systems/alchemy.js`）：**仍然是唯一自主供丹的路**

| 谁 | 能做什么 | 不能做什么 |
|---|---|---|
| 炼丹 | 任何丹，按 `baseRate`/`months`/丹炉等级自产 | — |
| 云深谷坊市 | 祛障丹**批量**（九折） | 不卖其它丹 |
| 万兽谷坊市 | 卖**成品**，溢价 ~2.9 倍 | **不解锁丹方**、不改 `ALCHEMY_RECIPES` |

⇒ 三条边界让炼丹的意义**增强了**而不是削弱：材料变便宜（玄铁宗补缺）⇒ 炼丹更顺；成品贵 3 倍 ⇒ 自炼有赚头；丹方只在科技线解锁 ⇒ `jiuzhuan`（九转丹房）的价值不变。

### 8.3 赋税（`mapYieldPerSec` / `mapYieldOf` / `advanceTerritories`）：**方向相同但不是同一件事**

- 赋税：**被动**、要有效镇守（`mapIsPacified`）、受民怨管理（`MAP_UNREST_PER_SEC`）、产出**灵石**
- 材料坊：**主动**、卖的是**同一块地产出的材料**、产出**灵石**
⇒ 材料坊的上游仍然是「占下来 + 守住」，它只是把**同一块地的第二种产出**变成灵石。二者**不替代**（产出量差 ~100 倍，§7.2）。10 座坊市也不可能取代领地，因为坊市数量上限就是 4（`foe` 节点数）。

### 8.4 城内「坊市」：**完全不同的东西，不要混**

城里已经有 `immortalmarket`（建筑，由凡人科技 `mutualmarket` 的 `unlocksBuilding` 解锁）、`cityMarketWorkers`、`CITY_MARKET_YIELD_PER_WORKER`、`CITY_MARKET_WORKERS_MAX` —— 那是**城内集市的人口分配**（凡人侧，产出银两）。
本文的坊市是**跨境兑换**（仙凡之间）。
⇒ **命名建议**：城内那个叫「**集市**」，本文的叫「**坊市**」（沿用 `CULTIVATOR_MARKET.name` 既有的「云深谷坊市」）。界面文案要区分，否则玩家会以为重复。

### 8.5 银两：**它的意义被加强了，不是被稀释**

银两原本的出口是建筑与科技（`cost`）。新增的`灵石→银两`**给了它一个新入口**，但被三道锁限住：
① `MARKET_SELL_MAX` 笔数上限；② `silverCap` 夹取（超出的蒸发）；③ 卖出 20% 折损。
⇒ 玩家不能「灵石换银两去刷科技」—— 换 60000 银两（`mutualmarket` 的 `cost`）在开局要 `0.3 / 0.8 = 0.375` 灵石，看似便宜，但**受笔数与 20% 折损**，且**银两本身由人口稳定产出**（`derive().silverPerSec`）。**待校准**：`MARKET_SELL_MAX = 6` 是否够松（要让「付大额科技」这个真实场景可用，又不至于让银两被灵石取代）。

## 九 · 两个预算的核算：秘闻（池子）与线索（余量）

> 任务书要求：**若不成立，明确说出来并给方案，不要假装没问题。**
> 货币换成秘闻之后，本题的答案**变好了**：**线索的余量完全不动**，代价是**多出一个更硬的预算 —— 20 条池子**。

### 9.1 预算 A：秘闻池子（**硬顶，不可再生**）

```
SECRETS.length = 20                  （src/data/trade.js 的 SECRETS，逐条数过）
Σ商品价格      = 28                  （§4.3）
⇒ 一周目最多买 5 件 ⇒ 必放弃 ≥ 2 件
⇒ 单件最贵 6 条 ≤ 20                 ✓ 断言 1
```

**判定：这是一条「刻意绑定」的预算**（§4.4），不是欠账 —— 主策裁决 (甲) 明确要求 `Σ > 池子`，理由是没有排他取舍就没有「消耗品」的手感。
**但池子不可再生**，所以三条兜底必须同时存在，缺一条就变成「不可逆的坑」：

1. **预算可见**（界面三数，断言 2）
2. **花费只能发生在已开放的坊市里** ⇒ **典型**分散到 4 个时点（§4.5 第 2 条；⚠ 不被强制，反例见 §4.5.1）
3. **轮回不保留 `secrets` / `secretsUsed`** ⇒ 分配可重来（§4.6，已实测 `REINCARNATION_KEEP`）

**若三条都做不到，就必须退回「Σ ≤ 20」**（全都买得起、无取舍）—— 那时请**改价目**，**不要改断言**。

### 9.2 预算 B：线索余量（**本块不再消耗它 ⇒ 余量保持 +34%**）

#### 供给侧（**只使用现口径**，旧口径已被设计师撤回）

- **慢路**（不投帖）：`cluePerSecFlat` 两个仙道科技节点 —— `tanxue`（探穴）`0.0002` + `jiexu`（界墟）`0.0004` = **0.0006 /秒 = 2.16 条/时**
- 全程 ≈ 44.6 游戏小时 ⇒ `2.16 × 44.6 = 96.3` 条
- 加上开局既有 ≈ 20 条 ⇒ **全期慢路供给 ≈ 116.3 条**（与 `immortal-techs.js` 的 `jiexu` 注释逐字一致，互为印证）
- **加速器**（投帖）：`advanceErrand` 用 `ERRAND_CLUE_PER_SEC = 2.5e-5` ⇒ 每人 **0.09 条/时**；10 人出门 = 0.9 条/时（并有 `ERRAND_DEATH_PER_SEC = 4e-6` 的死风险）

#### 需求侧（现口径四档）

| 档 | 线索需求 | 说明 |
|---|---|---|
| 硬需求 | 28 | 四次冲关的 `REALM_GATES[].clues`：筑基 2 + 金丹 4 + 元婴 8 + 化神 14 |
| 硬需求 + 洞天 | 39 | 洞天门票 `MAP_NODES[].clues`：1 + 2 + 3 + 5 = 11（另有 `fee` 灵石） |
| **一遍全参悟** | **87** | 参悟是最主要的汇：`MANUAL_ATTUNE_CLUE_COST = 2`、`MANUAL_ATTUNE_MAX = 5` |
| 满级 | 240 | 全部功法参悟到顶（**慢路永远不够**，必须投帖） |

#### 验算

```
慢路余量（一遍全参悟这一档） = 116.3 − 87 = 29.3 条   ⇒  相对需求 +33.7%（即 +34%）
本块从线索里拿走的           = 0 条
⇒ 余量仍是 29.3 条（+34%）
```

**⇒ 结论：成立，且比初稿更好。**
**初稿那句「余量从 +34% 掉到 +10.7%」随货币变更一并作废**（那是「用线索买商品」的算法）。

### 9.3 仍然存在的三条前提（变了，但没有消失）

1. **`Σ商品 ≤ 20 + 余量可放弃量`，且每件 `price_i ≤ 20`。** 前者的意思是：放弃量要有限（一周目放掉 2 件、而不是放掉 5 件）。**若商品再加，必须同时加价或加池**，不能只加件数。
2. **不得给某件商品开「投帖专属」的秘闻来源** —— 否则就把「投帖是加速器、不是必经之路」（`immortal-techs.js` 的 `jiexu` 注释明确不许改）改成必经之路。
3. **`secretsUsed` 必须是下标集合而不是计数**，且**门槛一律读累计**（§4.2）—— 否则「花费会关掉已开的门」，玩家永久卡死。
   ⚠ 这条最危险：**12 / 15 两个门槛在 `immortal-actions.js` 与 `main.js` 里各写了一份**，一处漏改就是「科技锁回去」。

### 9.4 备选方案

**方案 B（若仿真显示池子太紧）**：扩池 —— 但**必须同时降产出速率**（`MORTAL_ROUTE.secretChance` + 三项 `secretChance` 科技），否则扩到 40 也是第 2 小时满，只是把同一问题放大。**代价：牵动整条科技线数值 ⇒ 不属本块，需单独一轮。**
**方案 C（本文不采用，列出对照）**：商品权免费（占领即全开）。用户的「通过秘闻解锁」这条链路会消失。

## 十一 · 存档字段（**两个层级、三处白名单，缺一处就「写进去读不回来」**）

本块新增 **3 个字段**，它们**不在同一层**，所以迁移点也不同 —— 这是最容易漏的地方：

```
顶层（与 state.secrets 同级）
  state.secretsUsed = []                      // 已花费的秘闻下标集合（§4.2）

家族级（state.cultivation 下）
  state.cultivation.marketGoods     = {}      // { [siteId]: [goodId, ...] } 已买断的商品权
  state.cultivation.marketSellCount = 0       // 灵石→银两 已用笔数
```

**三处必改（实测的符号名）**

| # | 文件 · 符号 | 要做什么 |
|---|---|---|
| 1 | `src/core/save.js` · `serialize` | **顶层白名单**加 `secretsUsed`（紧挨着现有的 `secrets` 那一行）。⚠ 这是**最容易漏的一处**：`serialize` 是**手写顶层白名单**，漏写 ⇒ 每次读档静默清空（`meta` 字段当年就是这么丢的，`serialize` 里给它留了注释） |
| 2 | `src/core/save.js` · `hydrate` | ① 顶层：在现有 `secrets` 的重建块旁边加 `secretsUsed`，用**同一个下标过滤器**（`Number.isInteger(v) && v >= 0 && v < SECRETS.length`），并**再做一次子集归一化**：不在 `fresh.secrets` 里的下标一律丢弃（保证不变式 `secretsUsed ⊆ secrets`）；② 家族级：在 `fresh.cultivation[k] = raw.cultivation[k] === undefined ? v : raw.cultivation[k]` 那份白名单对象里加 `marketGoods` / `marketSellCount` |
| 3 | `src/systems/cultivation.js` · `repairCultivation` | 同一份 **cultivation 字段白名单**（现有键：`poolBlueprint` / `pool` / `compass` / `veins` / `mineLevel` / `mineWorkers` / `clues` / `cluePool` / `caveRuns` / `conquests`）加 `marketGoods` / `marketSellCount` |

**⇒ 第 2、3 两处是「同一规则写在两处」的老坑**（T-10 的 `save.js` **逐人**白名单是同一族的逐人版，这次是**家族级 + 顶层**两个版本）。按 `docs/91 §十三.6` 给出的既有做法：**两处各留一行注释指向对方**，写明「这是第二份，改一处必须改两处」。

**载入容错（逐项）**
- `secretsUsed` 缺失 ⇒ `[]`；非数组 ⇒ `[]`；元素非整数/越界 ⇒ 丢弃；**不在 `secrets` 里 ⇒ 丢弃**（子集归一化，见 上表 #2）
- `marketGoods` 缺失 ⇒ `{}`；`siteId` 不在 `MARKET_SITE_MAP` ⇒ **丢弃**（照 `worldOf` 清理野镇守记录的写法）；`goodId` 不在该坊市的 `goods` 里 ⇒ 丢弃
- `marketSellCount` 一律 `Math.max(0, Math.floor(Number(x) || 0))`
- ⚠ `SAVE_VERSION` **只写不校验**（全仓无读取它的分支）⇒ **版本号帮不上迁移**，只能靠上面三处 + 幂等兜底。这与 T-10 的结论一致。

**往返验证**：`scripts/savecompat.mjs` 的「全字段往返值比对」能抓住这类漏写（`docs/91 §十三.6` 附注里 `ui.ritesSeen` 就是被它抓住的）。⇒ 阶段 2 必须跑一次。
