# 凡人城池分支点子：让不同玩家走出不同的城

> 任务 t1[c2] 交付物。本文是**点子发散**，不是落地清单：所有数值一律标注
> 【数值构想·待校准】，正式定参前必须过 `scripts/balance.mjs` 三策略对照。
> 数据口径：`src/data/techs.js`（凡人 18 项）、`src/data/buildings.js`（11 座）、
> `src/data/trade.js`、`src/data/pills.js`、`src/core/config.js`、`src/core/formulas.js`、
> 以及 `docs/15-科技线.md` v2。
> 引用一律用符号名（常量 / 函数 / 科技 id），不引行号。

---

## 〇、总原则（每条分支都必须过这四道筛子）

1. **真实取舍，不许严格占优。** 两条分支摆在同一个玩家面前，他必须真的
   「想一想」，而不是一眼看出哪条是对的。检验方法：能不能各说出一种
   「这条明显更好」的局面。说不出来就是废分支。
2. **不破坏 `docs/15-科技线.md` §一的四条设计支柱**——尤其「数字稳稳长大」
   与「主线凡人→仙道单向」。分支只能加在**并列层**，绝不能加在主线上
   （主线科技被互斥掉 = 新型软锁）。
3. **尽量复用现有 effect 键。** 现有 10 个凡人侧键
   （见 `MORTAL_EFFECT_KEYS` 与 `EFFECT_LABELS`）已经能表达「银两 / 人口 /
   死亡率 / 秘闻 / 商路」全部维度。新键是最后的手段——按 `docs/15` §七的
   检查清单，新键要同时改累加器、文案表、消费点三处，缺一处就是静默失败。
4. **互斥是机制，不是数值。** 分支要成立，科技数据模型需要一个小机制
   （见 §五「通用机制构想」），四个分支点共用这一份机制。

## 一、锚点组：商道「探秘者 ↔ 稳健」（用户点名，必须写全）

### 1.1 现状解析（解析推导，非感觉）

凡人商路（`MORTAL_ROUTE`）：每趟成本 100 银、耗时 25 秒、回报倍率 1.6、
秘闻概率 `secretChance = 0.01`（1%）。一趟净赚 = 100×1.6 − 100 = **60 银**。

探秘者（`seeker`，T4，1800 银，requires `trade`）：

| 效果键 | 值 | 实际后果 |
|---|---|---|
| `tradeIncome` | −0.30 | 每趟回报 160→112，**净赚 60→12 银**（−80%） |
| `deathFlat` | +0.004 | 全族死亡率 +0.40%/秒 |
| `secretChance` | +0.05 | 每趟秘闻概率 1%→**6%**（×6） |

**秘闻一侧的账**：开门要 `SECRET_UNLOCK = 10` 条秘闻，池子 `SECRETS` 共 20 条、
抽过不重复（不放回）。抽中次数的期望按优惠券收集问题估：

```
E(抽中次数) ≈ 20 × (H₂₀ − H₁₀) ≈ 20 × (3.598 − 2.929) ≈ 13.4 次
```

| | 不点探秘者（1%/趟） | 点探秘者（6%/趟） |
|---|---|---|
| 期望趟数 | ≈ 1340 趟 | ≈ 223 趟 |
| 单商队位连续跑（25 秒/趟） | **≈ 9.3 小时** | **≈ 1.6 小时** |
| 开门时间差 | — | **早 ≈ 7.8 小时**（每商队位） |

**银两一侧的账**：同在这 223 趟的窗口里——

| | 每趟净赚 | 223 趟累计 |
|---|---|---|
| 不点任何分支 | 60 银 | ≈ 13.4k 银 |
| 探秘者 | 12 银 | ≈ 2.7k 银 |
| 稳健（构想 A，+30%） | 108 银 | ≈ 24.1k 银 |

**死亡一侧的账**：`deathFlat +0.004` 是全族口径，与基础死亡率
`BASE.deathRate = 0.010`（1.0%/秒）同量级——作为对照，一座演武台
`ARENA_DEATH = 0.0006`、一座商队驿站 `CARAVAN_DEATH = 0.0008`，
探秘者一项科技 = **6.7 座演武台**的死亡压力。它不是点缀，是重税，
必须靠田地（`FIELD_BIRTH`）与后期的义庄（`yizhuang`，deathFlat −0.0012）补回来。

**结论**：探秘者现在的定位是「拿 ~10k 银 + 一份重死亡税，买 ~7.8 小时
（每商队位）的开门提前量」。这是一笔真实的交易，不是白送——
`docs/15` 把它列为「第一次真正的取舍」是准确的。**但它没有对手**：
不点它没有任何替代路线，只有「慢慢磨 1%」。这就是稳健分支要填的空位。

### 1.2 提议的稳健分支

| 项 | 内容 |
|---|---|
| 名称 | **稳健**（行商）（用户点名） |
| id 构想 | `steady` |
| 阶位 / 前置 | T4，requires `trade`——与 `seeker` 同层同前置，构成并列 |
| 成本 | 2000–2600 银【数值构想·待校准】（比 seeker 的 1800 略贵：它买的是「确定的钱」，确定性本身值钱） |
| 效果构想 A（纯粹版） | `tradeIncome +0.30`，其余不动（秘闻保持基础 1%） |
| 效果构想 B（低波动版） | `tradeIncome +0.25` · `deathFlat −0.0003`（商队走熟路、结伴昼行，人也折得少） |
| 叙事 | 「不走门路，只走熟路。什么年成该贩什么货，账房里有三十年的老账——山野间的风声听不见，但银子一文不少。」 |

两个构想都**不给任何秘闻加成**（用户硬要求：不提供秘闻收益）。
构想 B 的 `deathFlat −0.0003` 会顺带抵消半座驿站的死亡，「稳健」的手感更完整；
代价是要重新过一遍死亡账本【数值构想·待校准，两案取其一】。

### 1.3 为什么这是真实取舍而不是严格占优

| 维度 | 探秘者 | 稳健 |
|---|---|---|
| 坊市开门（10 秘闻） | ≈ 1.6 小时/商队位 | ≈ 9.3 小时/商队位（与「不点」相同） |
| 开门前的银两积累 | ≈ 2.7k（223 趟窗口） | ≈ 24.1k（同窗口） |
| 死亡税 | +0.40%/秒（重） | 0（构想 B 为 −0.03%/秒） |
| 后置解锁链 | `yizhuang`、仙道 `lingmai` 的前置 | 见 §1.4——**必须处理，否则被锁** |
| 谁明显更好 | 赶仙途、想早开炼气篇的玩家 | 经营流、离线挂机多、怕死人的玩家 |

逐项都有「这条明显更好」的局面 → 通过筛子 1。
注意开门时间差可以被**多盖商队驿站**摊薄（每多一座 `caravan` 多一路并行的 1%），
所以稳健玩家并非永远慢 7.8 小时，他只是要用银两（盖驿站、占营造格、
吃 `CARAVAN_DEATH`）来追——这本身就是第二层取舍，是健康的。

### 1.4 必须处理的整合问题（这一组的头号风险）

现有两个节点把 `seeker` 写死在 requires 里：

- `yizhuang`（义庄，T6）：requires `['household', 'seeker']`
- 仙道 `lingmai`（灵脉感应，T4）：requires `['seeker', 'zhenyue']`

若探秘者与稳健**互斥**，选稳健的玩家将永远点不了义庄、灵脉感应——
一条 T4 的分支选择锁死 T6/仙道科技，这违反支柱 3（锁只能给「更多」，不能给「许可」）。

三个处理方案（按推荐排序）：

1. **「分支组」前置**：义庄与灵脉感应的前置从「`seeker`」改为
   「`seeker` 或 `steady` 任一」。叙事上成立：义庄要的是「族里有人常在外面跑」，
   灵脉感应要的是「凡人的商路网络」——走熟路的一样满足。
   机制上对应 §五的 `requiresAny` 构想。
2. **互斥但可回头**：分支不锁死，回头点另一条时按原价 ×1.5 收「改弦更张费」
   【数值构想·待校准】。实现最省，但削弱了「选择有重量」的初衷，不推荐单用。
3. **不互斥**：两项都能点。最差——探秘者的死亡税可以被稳健的收益对冲，
   合成「全都要」的严格占优解，直接违反筛子 1。**排除**。

### 1.5 接口清单（符号名）

- 数据：`TECHS` / `TECH_MAP`（新增一项）；`EFFECT_LABELS` 无需新增
  （`tradeIncome`、`deathFlat` 已有文案）——**本组不需要新 effect 键**。
- 结算：`formulas.tradeReward()`（`tradeIncome` 已接线）、
  `formulas.derive()` 的 `deathRate`（`deathFlat` 已接线）、
  `formulas.tradeSecretChance()`（不动：稳健不给 `secretChance`）。
- 机制：`isTechUnlocked()` / `techStatus()` 需要认识互斥与「任一前置」（见 §五）。
- 冒烟：孤儿节点规则要求新科技必须有后继——`steady` 由方案 1 的
  `requiresAny` 接住（成为 `yizhuang` / `lingmai` 的可选前置），不违反规则。

## 二、分支点二：税赋与人丁「苛捐 ↔ 仁政」

**天然分支点的理由**：T5 的 `arithmetic`（算学，incomeMult +0.10）与
`household`（户籍，birthFlat +0.001）是同源的两种国策——一个刮钱、一个养人，
但目前只是「都点」，没有对立。银两与人口共用同一个乘数池
（`derive()` 的 `silverPerSec = population × BASE.silverPerPop × (1 + incomeMult + …)`），
在它们之间做一道非此即彼，张力是现成的。

### 2.1 两条分支

| | 苛捐（构想 id `levy`） | 仁政（构想 id `benevolence`） |
|---|---|---|
| 定位 | 激进刷资源：把人丁折成现银 | 稳健经营：薄赋养人，人口复利 |
| 阶位 / 前置 | T5，requires `finance` + `household` | 同左 |
| 成本 | 3200–4200 银【数值构想·待校准】 | 同左 |
| 效果构想 | `incomeMult +0.18` · `birthFlat −0.0004` | `incomeMult +0.03` · `birthFlat +0.0012` |
| 叙事 | 加派丁银，城里的银子厚了，生孩子的底气薄了 | 轻徭薄赋，敢生敢养，库房进得慢些 |

### 2.2 解析推导：分支价值随「住房饱和度」切换

关键观察：出生率的价值**不是无限复利**。人口被住房软上限压着
（`CROWD.threshold`：占用率 75% 以上拥挤死亡率 `CROWD.k × over²` 开始咬人），
所以 `birthFlat` 的真实作用是「**更快顶到容纳量**」，顶到之后边际归零；
而 `incomeMult` 在人口饱和后是**纯赚**。

- **饱和前**（城还在长）：仁政占优。粗锚【数值构想·待校准】：人口 800、
  净增速 0.5%/秒 时，仁政多出的 +0.16%/秒出生 ≈ 每小时多 ~23 人，
  这些人立刻进入 `silverPerPop = 0.12` 的产出池，且为作坊
  （`CITY_WORKSHOP_WORKERS`）与坊市用工（`CITY_MARKET_YIELD_PER_WORKER`）供人。
- **饱和后**（住房顶死）：苛捐占优。+0.18 vs +0.03 的差 = 0.15×0.12×人口，
  人口 800 时 ≈ **14.4 银/秒 ≈ 5.2 万银/时**【数值构想·待校准】，
  而仁政的出生加成全部撞在拥挤上蒸发。

所以这不是「前期选 A 后期选 B」的假分支，而是**按玩法分岔**：
狂盖房产（`house`）撑容纳量的经营流，仁政全程有用；
营造格紧张、人口长期顶着软上限的玩家，苛捐是纯增益。
一个分支的价值由玩家**另一条线上的营造习惯**决定——这正是「不同玩家不同体验」。

### 2.3 接口清单

- 结算：`derive()` 的 `birthRate`（`birthFlat` 已接线）与
  `silverPerSec`（`incomeMult` 已接线）。`EFFECT_LABELS` 两键都有文案。
  **不需要新 effect 键。**
- 机制：互斥（§五）。后继问题：`arithmetic` 现有后继是 `jixian`；
  两条新分支可共同作为某个 T6 节点的 `requiresAny` 候选，或暂挂
  「被 T7 乡贤祠 `xiangxian` 认作可选声望来源」【整合方式·待校准】。

## 三、分支点三：城坊用工「三班倒 ↔ 休耕」

**天然分支点的理由**：仙凡经济的城市一侧（药圃 `herbhouse` / 矿寮 `minestop` /
纸坊 `papermill` / 仙凡坊市 `immortalmarket`）目前只有一种玩法——铺作坊、
摊人口、吃 `CITY_LABOR_DEATH = 0.0000001`/人/秒 的固定折损。
`docs/15` §3.3 把它设计为「咬得住、但咬不死」的张力，
但玩家对它**没有任何调节手段**：想多要材料只能多铺作坊（多吃格位与分摊），
想少死人只能拆作坊。给这个旋钮装上一对分支，仙道冲刺流和保人经营流就分开了。

### 3.1 两条分支

| | 三班倒（构想 id `overwork`） | 休耕（构想 id `fallow`） |
|---|---|---|
| 定位 | 激进：材料为王，人是耗材 | 稳健：材料薄收，人丁不伤 |
| 阶位 / 前置 | T6，requires `arithmetic`（账房才排得开三班） | 同左 |
| 成本 | 7000–9000 银【数值构想·待校准】 | 同左 |
| 效果构想（推荐） | **新键 `laborDeathMult +2.0`** · `cityMaterialMult +0.40` | **新键 `laborDeathMult −0.6`** · `cityMaterialMult −0.05` |
| 效果构想（兜底，不加新键） | `deathFlat +0.0004` · `cityMaterialMult +0.40` | `deathFlat −0.0002` · `cityMaterialMult −0.05` |
| 叙事 | 炉火昼夜不熄，作坊三班轮转；料出得快，人折得也快 | 人歇地也歇，一年只作三季；出料薄些，族里无哭声 |

### 3.2 解析推导：量纲陷阱与粗锚

⚠ **口径陷阱**：`CITY_LABOR_DEATH` 只作用于**实际用工人数**
（`derive()` 的 `laborDeath = laborWorkers × CITY_LABOR_DEATH`），
而 `deathFlat` 作用于**全族**。用 `deathFlat` 模拟「三班倒」会误伤不做工的人，
所以推荐案引入新键 `laborDeathMult`，只乘在 `laborDeath` 一项上。
这是四个分支点里**唯一推荐新增 effect 键**的地方——若落地时想省这一步，
用兜底案并在文档里写明口径差异。

粗锚【数值构想·待校准】：用工 1000 人时，
现状折损 = 1000 × 1e-7 = 0.0001 人/秒 ≈ 每小时 0.36 人（几乎无感）；
三班倒 ×3 = 每小时 ~1.1 人——相对人口 2000 时每秒 22 人的自然出生仍是
「咬得住」，但已经是原来的三倍，叠上演武台/驿站/探秘者时会把城推进
「必须补田地」的状态。材料一侧 +0.40 等于白捡半项 `lingtian`（+0.50），
所以要拿三倍的折损去换。

### 3.3 接口清单

- 结算：`derive()` 的 `laborDeath`（推荐案在此乘 `laborDeathMult`）与
  `cityHerbPerSec / cityOrePerSec / cityRunePerSec`（`cityMaterialMult` 已接线，
  凡人与仙道科技共用 `techEffects()` 累加器，凡人科技带这个键数值上可用，
  但登记口径见下）。
- 若加新键：按 `docs/15` §七清单走三处——`MORTAL_EFFECT_KEYS`（或按结算位置
  归 `IMMORTAL_EFFECT_KEYS`，由主策定）、`EFFECT_LABELS`、`derive()` 消费点，
  smoke 的两条对齐断言会自动盯。
- 消费 `cityMaterialMult` 的另一处：`systems/immortal-economy.js` 的
  `advanceCityWorkshops()`——落地时确认它读的是同一份 `fx`。
- 机制：互斥（§五）。

## 四、分支点四：祛障丹「命数 ↔ 温补」（方差分支）

**天然分支点的理由**：`quzhangdan`（祛障丹）是凡人篇的最后一道门——
1 灵石/枚（`PILL_STONE_COST`）、25% 成算（`PILL_QI_CHANCE`），
期望 4 灵石出一名炼气。这是一个**几何分布**：首枚即成的概率 25%，
但连吃 4 枚不中的概率高达 (0.75)⁴ ≈ 31.6%——同样 4 灵石的期望，
有人 1 灵石进门，有人 6 灵石还在门外。这正是风险偏好型玩家的天然分岔口，
而且**期望值可以做得完全相等**，是纯方差选择，最干净的一类分支。

### 4.1 两条分支

| | 命数（现状，不动） | 温补（构想：新丹 `wenbudan` + 解锁科技 `wenbu`） |
|---|---|---|
| 丹 | 祛障丹：1 灵石，25% | 温补丹：**2 灵石，50%**（或 3 灵石 75%）【数值构想·待校准】 |
| 期望成本 | 4 灵石/修士 | 4 灵石/修士（严格相等） |
| 方差 | 大：25% 一发入魂；31.6% 吃 4 枚不中 | 小：两枚之内 75% 落定（或一枚 75%） |
| 代价 | 可能连黑，灵石沉没 | **放弃爆发力**：永远不可能 1 灵石进门 |
| 面向 | 赌徒 / 速通 / 多周目玩家 | 稳健规划 / 单周目怕黑的玩家 |

取舍成立的关键：两案期望严格相等时，温补只有在「放弃上限」的前提下
才不是严格占优——它不更便宜，只是更稳。灵石窘迫、只换得起一两笔的玩家
仍会赌命数；攒够了 4+ 灵石、求稳进炼气篇的玩家选温补。
（若落地时希望温补略有甜头，可把成算调到 55%，期望 3.64 灵石，
用「略亏上限换略赚期望」重新配平【数值构想·待校准】。）

### 4.2 接口清单

- 数据：`PILLS` / `PILL_MAP` 已有完整字段（`stoneCost`、`qiChance`、
  `requiresTech`），加第二枚丹**不需要改数据结构**；
  解锁科技 `wenbu` 建议挂 T6、requires `quzhang`（先见过门，才谈怎么敲）。
- 结算：`engine.planPill(state, pillId)` / `engine.commitPill(state, pillId)`
  **已经按 pillId 参数化**——这是现成接口，四个分支点里实现成本最低的一个。
- 界面：服丹按钮（`data-action="pill"` 与 app.js 的 `PILL_MAP.quzhangdan`
  引用处）需要泛化成「已解锁的丹列表」——这是本分支点的主要工程量。
- 机制：两种丹可以**不互斥**（都解锁、玩家按当下灵石存量选），
  也可以互斥（科技二选一）。**倾向不互斥**：丹是消耗品，选择发生在
  每一次服用时，比重在「每次都想想」而非「一次定终身」。
  此点交给主策裁决【整合方式·待校准】。

## 五、通用机制构想：互斥与「任一前置」（所有分支点共用）

现状数据模型里，科技之间只有「前置」一种关系（`requires` /
`requiresImmortal` / `requiresSecrets`）。分支化需要两个新字段（构想名，
由主策定名）：

| 构想字段 | 语义 | 消费点 |
|---|---|---|
| `excludes: ['seeker']` | 研习本项后，列出项永久锁定（反向同理） | `isTechUnlocked()` / `techStatus()`；UI 上被锁项显示「已选他途」而非「前置未满足」 |
| `requiresAny: [['seeker','steady']]` | 前置组：组内任一已研习即满足 | 同上；`yizhuang` 与仙道 `lingmai` 的 `seeker` 前置改写为前置组（§1.4 方案 1） |

硬约束（从既有规则推出）：

1. **孤儿节点规则**：新分支科技必须被某个后继的 `requires` / `requiresAny`
   接住，或带 `terminal: true`——否则 `balance.mjs --baseline` 的
   `auditTechs` 立刻报警。
2. **存档兼容**：只**新增**科技 id；旧 id 一律不改名不删除
   （`docs/15` 的既定规则）。老存档里没有 `excludes` 字段 = 无互斥，自然兼容。
   ⚠ 但「已同时研习 seeker 与 steady 的老存档」这种局面**不可能存在**
   （新 id 才出生），无需迁移逻辑。
3. **仙道侧的 requires 混排**：`isImmortalTechUnlocked()` 按 id 所属线分派判定，
   `requiresAny` 落地时这里要同步认识前置组，别让凡人分支 id 在仙道树里查空。
4. **effect 键优先复用**：四个分支点里，锚点组与税赋组**零新键**，
   祛障丹组零新 effect 键（走 pills 表），只有城坊组推荐一个新键
   `laborDeathMult`。新键越少，「三处清单」漏一处的风险面越小。

## 六、优先级建议与风险登记

| 序 | 分支点 | 理由 |
|---|---|---|
| 1 | §一 商道 探秘者 ↔ 稳健 | 用户点名；数值推导最完整；零新 effect 键；唯一硬依赖是 `requiresAny` 机制 |
| 2 | §四 祛障丹 命数 ↔ 温补 | 期望严格相等的纯方差分支；`planPill/commitPill` 接口现成 |
| 3 | §二 苛捐 ↔ 仁政 | 零新键；与住房软上限联动，取舍逻辑新颖，但 break-even 需仿真定参 |
| 4 | §三 三班倒 ↔ 休耕 | 推荐案要新键 `laborDeathMult`，三处清单 + 仙凡口径，落地最重 |

风险登记：

- **R1（§1.4）**：`seeker` 被 `yizhuang` / `lingmai` 写死为前置——不做
  `requiresAny` 就上线互斥 = 制造新型软锁。这是全文档唯一「不做就不能上」的项。
- **R2**：所有标【数值构想·待校准】的数，定参口径应与 `docs/15` §六一致
  （按解锁时点积分，不用 `Σ速率×T`——见 `docs/00` §1.3 原则 4 的警告）。
- **R3**：`balance.mjs` 的 AI 目前不会表达「风险偏好」——分支上线后仿真
  需要至少一条「选稳健线」的策略，否则三策略对照测不出分支是否严格占优。
  这与 `docs/15` §八欠账 4（AI 欠账）是同类问题，测量工具的欠账，不是设计的欠账。
- **R4**：互斥科技的 UI 文案要写成「已选他途」，不能复用「前置未满足」——
  否则玩家会以为还能回头点（参照 `techNameOf` 事故教训：静默降级是最坏的失败形态）。
